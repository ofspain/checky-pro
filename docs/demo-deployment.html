1What this is

The platform is a multi-service payment-dispute system — auth, crypto, payment, notification and intelligence services, built over months against specs and heavily tested suites. None of that had ever run anywhere but a laptop. This exercise took the leanest slice that still proves the core claim — paste a transaction hash, get an independent on-chain verdict — and put it on the public internet with a real certificate.

The slice is deliberately thin. No sign-in, no merchant dashboard, no invoices. One page, one endpoint, three services behind it, and three independent blockchain providers voting on what is true. Everything else in the platform is present on the box but unroutable.

The one result that matters A real Sepolia transaction, submitted to the public URL, returned outcome: AGREED, existence: AGREED, 26 confirmations and "0.01 WETH" with both addresses — every fact agreed 2-of-3 by three separate companies' nodes. That is the product's entire premise, executing on infrastructure defined in code.

1.1 What a visitor sees

A single page asking for a transaction hash. Paste one, and within a few seconds the page states whether that transaction exists on-chain, how many blocks have confirmed it, who sent it, who received it, and how much of which token moved. Four outcomes are possible, and three of them are refusals to overstate:

OutcomeWhat it meansWhy it is not just "valid / invalid"
AGREEDAll three providers independently returned the same facts. The payment is real and fully described.Agreement is the evidence, not one server's say-so.
HELDThe providers do not agree yet — typically a transaction seconds old that some nodes have seen and others have not.The honest answer when the chain itself has not settled. Impossible to produce locally.
UNKNOWN_TOKENThe transaction is real and the amount is known, but the token is not one this deployment can name.Refuses to label an arbitrary contract as "USDC". Shows the amount, withholds the name.
NOT_FOUNDNo such transaction.—

2Infrastructure as code — AWS CDK in Python

The infrastructure is one CDK app. It was originally scaffolded in TypeScript; that was corrected to Python, which is now the standard for infrastructure in this project (the engineering-standard document has been amended to match — it had carried the same error).

2.1 Entry point: refusing to do the dangerous thing quietly

app.py does almost nothing except guard two failure modes that are much worse when they are silent.

infra/deploy/cdk/app.pyCDK entry point
app = cdk.App()

# Both optional, and the default is no SSH at all: no open port and no key on the box.
#
# Ansible connects over SSM and the console connects through Session Manager, so an SSH rule
# protects nothing here while still being a rule that goes stale - a home address changes, and
# the entry then names a stranger's. Supply both of these together if you ever want SSH back.
ssh_cidr = app.node.try_get_context("sshCidr")
key_name = app.node.try_get_context("keyName")

# The one thing worth refusing outright. An address is a deliberate choice; the whole internet
# on port 22 is almost always a slip, and it is the slip this project should not make quietly.
if ssh_cidr and ssh_cidr.strip().endswith("/0"):
    raise SystemExit(
        f"Refusing sshCidr={ssh_cidr}: that is SSH open to the internet.\n"
        "Pass a single address, for example -c sshCidr=$(curl -s https://checkip.amazonaws.com)/32"
    )

# This stack looks up the default VPC, which CDK can only do for a named account and region.
# Without credentials the lookup fails several layers down as a jsii stack trace about a
# "context provider", which says nothing useful to the person who simply has not logged in yet.
account = os.environ.get("CDK_DEFAULT_ACCOUNT")
if not account:
    raise SystemExit(
        "No AWS account resolved, so the default-VPC lookup cannot run.\n"
        "Configure credentials and try again, for example:\n"
        "  aws configure                 # or\n"
        "  export AWS_PROFILE=<profile>  # for an SSO or named profile"
    )

The default is no SSH at all — no inbound port 22, and no key pair on the instance. This was not the starting position; it was arrived at deliberately after confirming that Ansible (over SSM) and the AWS console (over Session Manager) both work without it, which makes an open port 22 pure attack surface with no compensating use.

2.2 The stack

demo_stack.py is about 250 lines and creates: three ECR repositories, an S3 transfer bucket, a KMS key, a security group, an IAM role, one EC2 instance with user-data, and an Elastic IP. Each decision is recorded in the class docstring because each one differs from what the real platform will do.

infra/deploy/cdk/demo_stack.py — class docstringrationale
"""The demo's infrastructure.

The real platform is planned as CDK stacks split by blast radius - network, data, security,
edge, one per service, on EKS with RDS, MSK and KMS (infra/README.md). This is not that, and
is not trying to be: it is the demo, sized for a demo, written so the parts that matter later
are already expressed as code rather than clicked into a console.

Deliberate choices, each of which the real stack makes differently:

- **The default VPC is used, not a new one.** A private subnet needs a NAT gateway to pull
  images, which costs more per month than the instance. The box is public-subnet with a
  security group doing the work.
- **Postgres and Kafka run as containers, not RDS and MSK.** One box, one demo. The compose
  file keeps one database per service, so moving to RDS later is a connection string.
- **No load balancer.** Caddy terminates TLS on the box with Let's Encrypt, which is free and
  renews itself. An ALB with ACM is the production answer and costs about sixteen dollars a
  month to serve one page.
"""

Image repositories — pull only

demo_stack.pyECR
SERVICES = ("auth", "crypto", "payment")

# One repository per service. The box only ever pulls; images are built and pushed from a
# developer machine or CI, so the source tree never lands on an internet-facing host.
repositories = [
    ecr.Repository(
        self, f"Repo{service}",
        repository_name=f"checky-{service}",
        image_scan_on_push=True,
        removal_policy=RemovalPolicy.DESTROY,
        empty_on_delete=True,
        lifecycle_rules=[
            ecr.LifecycleRule(max_image_count=5, description="Keep the last five images.")
        ],
    )
    for service in SERVICES
]

empty_on_delete=True matters: without it cdk destroy fails on a repository that still holds images, and leaves the stack half-deleted.

The S3 bucket that exists only because SSM cannot carry files

demo_stack.pyS3
# Ansible reaches this box over SSM rather than SSH, and the aws_ssm connection plugin
# moves files through S3 because the Session Manager channel itself cannot carry them.
# The objects are transient, so they are expired after a day and the bucket is emptied
# when the stack is destroyed - otherwise `cdk destroy` leaves a bucket behind forever.
transfer_bucket = s3.Bucket(
    self, "SsmTransferBucket",
    block_public_access=s3.BlockPublicAccess.BLOCK_ALL,
    enforce_ssl=True,
    encryption=s3.BucketEncryption.S3_MANAGED,
    removal_policy=RemovalPolicy.DESTROY,
    auto_delete_objects=True,
    lifecycle_rules=[
        s3.LifecycleRule(
            expiration=Duration.days(1),
            abort_incomplete_multipart_upload_after=Duration.days(1),
        )
    ],
)

A KMS key, because a service refused to start without one

demo_stack.pyKMS
# auth-service envelope-encrypts TOTP seeds with a KMS data key (ADR-0003) and refuses
# to start outside the local profile without a key, rather than silently falling back to
# its fixed local-dev key. That guard is right, so the demo gets a real key. Nothing in
# the demo path signs in, so this is a startup requirement rather than a used feature -
# but a service that will not boot is not much use either way.
mfa_key = kms.Key(
    self, "MfaSeedKek",
    description="Checky demo: KEK for auth-service TOTP seed envelope encryption.",
    enable_key_rotation=True,
    removal_policy=RemovalPolicy.DESTROY,
    alias="alias/checky-demo-mfa-seed-kek",
)

Network: two ports open, and a third only on request

demo_stack.pysecurity group
# 80 is not optional: Let's Encrypt validates over it, and Caddy redirects it to 443.
security_group.add_ingress_rule(ec2.Peer.any_ipv4(), ec2.Port.tcp(80), "HTTP (ACME + redirect)")
security_group.add_ingress_rule(ec2.Peer.any_ipv4(), ec2.Port.tcp(443), "HTTPS")

# No SSH unless an address was named. Ansible connects over SSM and the console uses
# Session Manager, so with no key pair on the box an open port 22 cannot be authenticated
# against at all - it is surface with no use. Real break-glass for a broken agent is the
# EC2 Serial Console, which needs no inbound port, or destroying and redeploying this
# stack, which takes about four minutes and is the honest answer for a demo box.
if ssh_cidr:
    security_group.add_ingress_rule(
        ec2.Peer.ipv4(ssh_cidr), ec2.Port.tcp(22), "SSH, one address only"
    )

IAM: four grants, no more

demo_stack.pyIAM
role = iam.Role(
    self, "DemoInstanceRole",
    assumed_by=iam.ServicePrincipal("ec2.amazonaws.com"),
    managed_policies=[
        iam.ManagedPolicy.from_aws_managed_policy_name("AmazonSSMManagedInstanceCore")
    ],
)
# Pull only. The box has no business pushing an image.
for repository in repositories:
    repository.grant_pull(role)
role.add_to_policy(iam.PolicyStatement(actions=["ecr:GetAuthorizationToken"], resources=["*"]))
# Both ends of the SSM file transfer: the box reads what Ansible uploaded and writes
# back what Ansible fetches.
transfer_bucket.grant_read_write(role)
# GenerateDataKey and Decrypt, which is what envelope encryption needs. The containers
# pick these credentials up from the instance metadata endpoint via the default chain.
mfa_key.grant_encrypt_decrypt(role)

User-data: the minimum, and one architecture lesson

demo_stack.pyuser-data
user_data.add_commands(
    "set -eux",
    "dnf update -y",
    "dnf install -y docker python3 python3-pip",
    "systemctl enable --now docker",
    "usermod -aG docker ec2-user",
    "mkdir -p /usr/local/lib/docker/cli-plugins",
    # Architecture-matched, not hardcoded. A compose binary for the wrong architecture
    # still installs and still passes a file-exists check, then fails as "'compose' is
    # not a docker command" much later - which is exactly what an x86_64 download did on
    # this Graviton box. Ansible re-checks and repairs this, so a wrong one is survivable.
    'ARCH=$(uname -m)',
    "curl -fsSL https://github.com/docker/compose/releases/download/v2.32.1/"
    "docker-compose-linux-${ARCH} -o /usr/local/lib/docker/cli-plugins/docker-compose",
    "chmod +x /usr/local/lib/docker/cli-plugins/docker-compose",
    "install -d -o ec2-user -g ec2-user /opt/checky",
)

User-data installs only what must exist before Ansible can connect. All application configuration is Ansible's job, deliberately: user-data runs once at first boot, so anything put here can only be changed by replacing the instance.

demo_stack.pyEC2 + EIP

Measured, not assumed — instance sizing t4g.medium (Graviton, arm64, 2 vCPU, 3835 MB). Three JVMs, Kafka and Postgres share this box; payment-service alone took 188 seconds to start when all three booted together, so 2 GB leaves no headroom and an OOM during startup presents as a hang. arm64 was chosen because every image in the stack has an arm64 build (verified for postgres, kafka, flyway 11 and caddy) and the machines building them are Apple Silicon — so builds are native rather than QEMU-emulated, and the instance is cheaper besides.

3The containerised toolchain

Two frictions stood between this repository and a deploy, and both were removed by containerising the tool rather than documenting a prerequisite.

FrictionWhy it bitesResolution
CDK needs Node even for Python stacks The CDK CLI is a Node program, and jsii bridges Python to it. A Python-only image fails with '_NodeProcess' object has no attribute '_process'. cdk/Dockerfile on node:22-bookworm-slim with Python added.
aws-cdk-lib publishes wheels only for Python 3.11–3.13 On this machine's Python 3.15, pip fell back to building jsii from source and had not finished after ten minutes. The image pins Python 3.11.2, so the host's interpreter is irrelevant.
Ansible needs the SSM plugin, boto3 and two collections A long, version-sensitive install nobody should repeat by hand. ansible/Dockerfile, built once (~13 minutes), then cached.
infra/deploy/ansible/Dockerfileexcerpt
FROM python:3.12-slim
RUN pip install --no-cache-dir \
        "ansible-core==2.18.1" "boto3==1.35.90" "botocore==1.35.90" \
    && ansible-galaxy collection install "community.aws:9.0.0" "amazon.aws:9.0.0"
RUN set -eux; \
    case "$(uname -m)" in \
      x86_64)  ARCH=64bit ;; \
      aarch64) ARCH=arm64 ;; \
      *) echo "unsupported architecture $(uname -m)" >&2; exit 1 ;; \
    esac; \
    curl -fsSL "https://s3.amazonaws.com/session-manager-downloads/plugin/latest/ubuntu_${ARCH}/session-manager-plugin.deb" \
      -o /tmp/smp.deb; \
    dpkg -i /tmp/smp.deb; rm -f /tmp/smp.deb; \
    session-manager-plugin --version

3.1 Wrappers: ./cdk and ./play

Each image has a short shell wrapper that builds it once, mounts the repository, and forwards AWS credentials from the environment. Two details in them were corrected after they caused failures:

infra/deploy/cdk/cdk and ansible/playtwo fixes
# 1. A TTY only when there is one. `docker run -it` fails outright with no terminal
#    attached, which would break the moment either wrapper ran in CI.
if [ -t 0 ] && [ -t 1 ]; then TTY_FLAGS="-it"; else TTY_FLAGS=""; fi

# 2. ./play with no arguments must still run the playbook. The entrypoint is
#    ansible-playbook, so a bare `./play` was an argparse error rather than a deploy.
case "${1-}" in
  *.yml|*.yaml) ;;
  *) set -- playbook.yml "$@" ;;
esac
Credential handling Credentials were never written to ~/.aws and never committed. They live in a single 0600 file in a session scratchpad outside the repository, sourced into the environment for the length of a command, and forwarded into the container as environment variables. The repository's .gitignore covers .env, .env.* and inventory.ini; env.example is the only committed form and holds no real values.

4Configuration management — Ansible over SSM

The division of labour is strict. CDK creates infrastructure; Ansible configures the box and runs the application. Nothing is ever edited on the server — a change is made in git and the playbook runs again. The playbook is idempotent by construction, which is the whole point of it.

4.1 Connecting without SSH

Ansible reaches the instance through Session Manager, using the community.aws.aws_ssm connection plugin. Three consequences follow, and all three are improvements: there is no key to manage, no ansible_user to agree on, and port 22 need not be open for a deploy to work. The cost is that ansible_host must be an instance ID, and a transfer bucket is required because the Session Manager channel cannot carry files on its own.

infra/deploy/ansible/inventory.ini.exampleinventory
[demo]
checky-demo ansible_host=REPLACE_WITH_InstanceId

[demo:vars]
ansible_connection=community.aws.aws_ssm
ansible_aws_ssm_bucket_name=REPLACE_WITH_SsmTransferBucketName
ansible_aws_ssm_region=eu-west-1

# Break-glass, for when the SSM agent itself is what is broken. Requires that the stack was
# deployed with -c keyName=<your-key-pair>, and that your address is still the one in sshCidr:
#
#   ./play -e ansible_connection=ssh \
#          -e ansible_host=REPLACE_WITH_PublicIp \
#          -e ansible_user=ec2-user \
#          -e ansible_ssh_private_key_file=/root/.ssh/REPLACE_WITH_YOUR_KEY.pem

4.2 Escalation, because the connection user differs by transport

infra/deploy/ansible/playbook.ymlplay header
- name: Deploy the Checkychain verification demo
  hosts: demo
  # Root, because the connection user differs by transport and neither can do the work as itself.
  # Over SSM the session runs as `ssm-user`, which is not in the docker group and cannot write to
  # /opt/checky; over SSH it is `ec2-user`, which can do both. Escalating makes the two identical,
  # and the files are still owned by ec2-user so that a human who logs in can manage the stack.
  become: true
  gather_facts: true

4.3 Failing early and in English

The playbook reads .env on the control machine, asserts every key the compose file will demand, and says what is missing — rather than failing deep inside a template or, worse, starting a stack that will crash-loop.

4.4 The readiness check that was rewritten

This is the most instructive change in the playbook. The original waited for the compose plugin's path to exist — which a binary for the wrong architecture satisfies perfectly.

Presence is not usability An x86_64 compose binary on this arm64 box passed a wait_for path check, and then failed four tasks later as unknown flag: --quiet — an error that points at the wrong thing entirely. file on the binary reported "ELF 64-bit LSB executable, x86-64". The check now runs the thing, and repairs it if it cannot.
playbook.ymlprobe and self-repair
- name: Wait for the Docker daemon that user-data installs
  ansible.builtin.command: docker info
  register: docker_info
  until: docker_info.rc == 0
  retries: 60
  delay: 10
  changed_when: false

- name: Find out whether the compose plugin actually runs here
  ansible.builtin.command: docker compose version
  register: compose_probe
  failed_when: false
  changed_when: false

- name: Install the compose plugin built for this machine's architecture
  ansible.builtin.get_url:
    url: "https://github.com/docker/compose/releases/download/v2.32.1/docker-compose-linux-{{ ansible_architecture }}"
    dest: /usr/local/lib/docker/cli-plugins/docker-compose
    mode: "0755"
    force: true
  when: compose_probe.rc != 0

- name: Prove the plugin runs, rather than merely exists
  ansible.builtin.command: docker compose version
  register: compose_version
  changed_when: false

4.6 Two gates after publishing

The playbook does not end at docker compose up. It verifies the result from the control machine, over the public internet — which is the only perspective that counts.

playbook.ymlpost-deploy gates
- name: Wait for the landing page to answer over HTTPS
  ansible.builtin.uri:
    url: "https://{{ deploy_env.PUBLIC_HOST }}/"
    status_code: 200
  register: landing
  until: landing.status == 200
  retries: 30
  delay: 10
  delegate_to: localhost
  become: false

# The check that matters is the one performed after publishing, not before.
- name: Prove that nothing but the demo is reachable
  ansible.builtin.uri:
    url: "https://{{ deploy_env.PUBLIC_HOST }}/{{ item }}"
    status_code: 404
  loop:
    - login
    - oauth2/authorize
    - admin
    - accounts
    - api-keys
    - app/
    - api/v1/invoices
    - api/v1/receipts
    - actuator/health
    - userinfo
  delegate_to: localhost
  become: false

The second gate is a negative test on the live site: ten paths that exist in the platform and must not be exposed by this deployment. If a future change to the Caddyfile accidentally routes /actuator/health or the whole SPA, the deploy fails rather than succeeding quietly. All ten returned 404.

5Runtime topology — Docker Compose

Six containers run; two more run to completion and exit. Only edge publishes ports.

infra/deploy/compose.prod.yamlheader + shared env
# The demo on one EC2 box. Deployed by infra/deploy/ansible, never edited on the server.
#
# Images are pulled from ECR; nothing is built here. A public-facing box has no business holding
# the source tree, a Maven cache and a JDK.
#
# Only `edge` publishes ports. Everything else talks over the compose network, so auth-service and
# the two application services are not reachable from the internet at all.
name: checky-demo

x-java: &java
  restart: unless-stopped
  logging:
    driver: json-file
    options: { max-size: "10m", max-file: "3" }

x-java-env: &java-env
  SPRING_PROFILES_ACTIVE: prod
  KAFKA_BOOTSTRAP_SERVERS: kafka:9092

The file ownership bug — and why it was nearly invisible The playbook escalates to root, so the rendered file was root-owned 0600. Postgres runs as uid 70 inside postgres:16-alpine. The entrypoint logged Permission denied, created none of the three databases, and carried on — while still marking the data directory as initialised, so the script would never be retried. Every later connection failed with "database … does not exist". The fix sets the owner explicitly; the mode stays 0600 because the file carries the role passwords.
playbook.ymlthe fix
- name: Render the database initialisation script
  ansible.builtin.template:
    src: init.sql.j2
    dest: "{{ app_dir }}/config/init.sql"
    # Owned by uid 70, which is what postgres runs as inside postgres:16-alpine (checked with
    # id, not assumed). The playbook escalates to root, so without this the file is root-owned
    # and the container cannot read it: the entrypoint reports "Permission denied", creates no
    # databases, and every later connection fails with "database ... does not exist" while the
    # data directory still counts as initialised. 0600 not 0644 on purpose - this file carries
    # the app role passwords, so no other user on the host should be able to read it either.
    owner: "70"
    group: "70"
    mode: "0600"
  no_log: true

6The edge — TLS, routing and default-deny

Caddy terminates TLS, obtains and renews a Let's Encrypt certificate without configuration, and routes exactly four things. Everything else returns 404 — not by omission, but by an explicit final block.

infra/deploy/config/Caddyfilecomplete
# The public surface, and nothing else.
#
# Caddy obtains and renews a Let's Encrypt certificate for PUBLIC_HOST automatically, which is why
# the box needs ports 80 and 443 open and the DNS record pointing at it before the first start.
# No `email` directive: Let's Encrypt permits an ACME account with no contact address, and
# certificates issue and renew identically without one. The only thing given up is expiry warning
# mail. To turn that on, add `email you@example.com` inside a global block here.

{$PUBLIC_HOST} {
	encode zstd gzip

	header {
		Strict-Transport-Security "max-age=31536000"
		X-Content-Type-Options "nosniff"
		X-Frame-Options "DENY"
		Referrer-Policy "no-referrer"
		# The page loads nothing from anywhere else; its CSS and JS are inline.
		Content-Security-Policy "default-src 'none'; img-src 'self'; style-src 'unsafe-inline'; script-src 'unsafe-inline'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'"
		-Server
	}

	handle /api/v1/verifications      { reverse_proxy payment:8083 }
	handle /api/v1/verifications/*    { reverse_proxy payment:8083 }
	handle /logo.png                  { root * /srv/landing
	                                    file_server }

	# The landing page and every receipt link are the same single file.
	handle /r/*  { root * /srv/landing
	               rewrite * /index.html
	               file_server }
	handle /     { root * /srv/landing
	               rewrite * /index.html
	               file_server }

	# Everything else - auth, the merchant API, the SPA, actuator - is simply not routed here.
	handle { respond "Not found" 404 }
}

The security headers are strict because they can be: the page loads nothing from any other origin, so default-src 'none' with an explicit connect-src 'self' is achievable rather than aspirational.

On the ACME contact address No email directive is present, by instruction and by design. Let's Encrypt permits an ACME account with no contact address, and certificates issue and renew identically without one; the only thing forgone is expiry-warning mail. An earlier draft left email {$ACME_EMAIL} in place with an empty variable — which renders as a bare email and is not valid Caddy. Removing the directive entirely is the correct form; an empty value would have been worse than an absent one.

9What this achieves, and what it does not

9.1 From a user's point of view

Someone who has been sent a payment and a transaction hash can, with no account and no software, paste that hash into a public web page and learn — within seconds, from three independent sources — whether the payment is real, how settled it is, and exactly what moved. The page will say "not yet" when the chain has not settled, and will refuse to name a token it cannot identify. That refusal is the product: a verification service that overstates its confidence is worse than none.

9.2 What it proves to the team

  • The three services genuinely interoperate outside a developer machine, including real OAuth2 client_credentials between payment and crypto.
  • The 2-of-3 quorum works against real, disagreeing providers — and HELD, which no local test could ever produce, was observed.
  • The whole environment is reproducible from this repository: ./cdk deploy then ./play, from any machine with Docker and credentials. No console clicking, no undocumented state.
  • The startup guards built months ago (KMS, screening mode, signing key) all fired correctly the first time they were outside local. They were not theatre.

9.3 Limitations — stated plainly

LimitationDetailWhat would fix it
Public RPC endpoints, no SLA All three providers are free, unauthenticated, shared endpoints. thirdweb threw 429 retry-after: 135 after a single request; 1rpc.io blocks AWS entirely. The three now in use passed 10/10, but nothing contractually stops them throttling mid-demo — and if two of three throttle, the quorum cannot form and the answer becomes a 503. Single box, no redundancy One EC2 instance runs Postgres, Kafka and three JVMs on 3835 MB. No HA, no failover, no autoscaling. An instance failure is total downtime. The planned EKS + RDS + MSK stacks.
No backups Data lives in Docker volumes on one EBS volume with delete_on_termination=True. cdk destroy discards everything. Acceptable for a demo that stores no customer data; unacceptable for anything else. RDS with automated snapshots.

11The last mile — a real domain behind Cloudflare

Today the site answers on 54-216-107-16.sslip.io, a wildcard DNS service that resolves any dashed-IP hostname to that IP. It is genuinely useful — it earned a real Let's Encrypt certificate — but it is not a name anyone should be given. This section is the full procedure to move to an owned domain fronted by Cloudflare.

11.1 The decision that shapes everything else: who holds the certificate

Read this before turning the orange cloud on Caddy currently gets its certificate over the HTTP-01 challenge, which requires Let's Encrypt to reach port 80 on the origin. Once Cloudflare proxies the hostname, Cloudflare terminates TLS at its edge and the origin is no longer directly addressable — so HTTP-01 renewal becomes unreliable or impossible. Enabling the proxy without changing certificate strategy is the single most common way to break this setup, and it breaks at renewal, sixty days later, not at switch-over.

Two workable strategies, in order of preference:

StrategyHow it worksTrade-off
A. Cloudflare Origin CA recommended Cloudflare issues a long-lived (up to 15-year) certificate valid only between its edge and your origin. Caddy serves it with an explicit tls directive and stops talking to Let's Encrypt entirely. Cloudflare presents its own public certificate to visitors. No ACME on the origin at all — nothing to renew, nothing to break. Requires SSL mode Full (strict).
B. DNS-01 with a Cloudflare API token Caddy keeps using Let's Encrypt but proves control via a DNS TXT record instead of port 80, so the origin need not be reachable. Needs a custom Caddy image (the Cloudflare DNS module is not in the standard build) and a scoped API token on the box.

11.2 Procedure — strategy A, step by step

Step 1 · Add the domain to Cloudflare

Add the zone in the Cloudflare dashboard and change the nameservers at the registrar to the two Cloudflare assigns. Propagation is typically minutes to a few hours. Cloudflare's own activation check confirms it.

Step 6 · Lock the origin to Cloudflare

With the proxy enabled, anyone who learns the IP can still bypass Cloudflare and hit the origin directly — defeating the rate limiting and WAF entirely. The security group should accept 80 and 443 only from Cloudflare's published ranges.

demo_stack.py — replacing the two any-ipv4 rulesCDK
# Cloudflare's published edge ranges, from https://www.cloudflare.com/ips-v4
# Fetch them at synth time rather than pasting a list that will silently go stale:
#   curl -s https://www.cloudflare.com/ips-v4
# Treat the fetched list as data: validate each entry parses as a CIDR before using it.
cloudflare_v4 = app.node.try_get_context("cloudflareIpsV4")  # newline- or comma-separated

if cloudflare_v4:
    for cidr in [c.strip() for c in cloudflare_v4.replace(",", "\n").split() if c.strip()]:
        security_group.add_ingress_rule(ec2.Peer.ipv4(cidr), ec2.Port.tcp(443), "Cloudflare edge")
        security_group.add_ingress_rule(ec2.Peer.ipv4(cidr), ec2.Port.tcp(80), "Cloudflare edge")
else:
    # Fallback: open, as today. Only correct while the hostname is unproxied.
    security_group.add_ingress_rule(ec2.Peer.any_ipv4(), ec2.Port.tcp(80), "HTTP (ACME + redirect)")
    security_group.add_ingress_rule(ec2.Peer.any_ipv4(), ec2.Port.tcp(443), "HTTPS")
A sturdier alternative Cloudflare Tunnel (cloudflared as a container in the compose file) removes inbound ports altogether: the box dials out to Cloudflare and nothing needs to be open. That is strictly better than an IP allowlist, which goes stale whenever Cloudflare adds a range. It costs one more container and a tunnel token.

Step 7 · Recover the real client IP

Behind a proxy, every request appears to come from a Cloudflare address. Caddy must be told to trust the proxy before it will believe the forwarded header — otherwise logs and any origin-side rate limiting see only Cloudflare.

# Cloudflare sends the visitor's address in CF-Connecting-IP. Caddy will only believe a
# forwarded address from a proxy it has been told to trust, which is the correct default:
# otherwise any client could spoof its own source address by setting the header.
{
	servers {
		client_ip_headers CF-Connecting-IP X-Forwarded-For
		trusted_proxies static 173.245.48.0/20 103.21.244.0/22 # ... the full Cloudflare list
	}
}

12.2 Access without SSH

  • Console: EC2 → Connect → Session Manager. The session lands as ssm-user.
  • sudo cd /home/ec2-user cannot work — cd is a shell builtin, not a program. Use sudo -i or sudo su - ec2-user. The home directory is mode 700, which is why ssm-user cannot enter it.
  • The application is at /opt/checky. Do not edit it: the playbook overwrites it on the next run. Change the repository instead.
  • The Java images contain no shell, so docker compose exec payment sh fails by design. Use docker compose logs.
