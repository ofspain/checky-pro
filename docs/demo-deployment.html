1What this is

The platform is a multi-service payment-dispute system — auth, crypto, payment, notification and intelligence services, built over months against specs and heavily tested suites. None of that had ever run anywhere but a laptop. This exercise took the leanest slice that still proves the core claim — paste a transaction hash, get an independent on-chain verdict — and put it on the public internet with a real certificate.

The slice is deliberately thin. No sign-in, no merchant dashboard, no invoices. One page, one endpoint, three services behind it, and three independent blockchain providers voting on what is true. Everything else in the platform is present on the box but unroutable.

The one result that matters A real Sepolia transaction, submitted to the public URL, returned outcome: AGREED, existence: AGREED, 26 confirmations and "0.01 WETH" with both addresses — every fact agreed 2-of-3 by three separate companies' nodes. That is the product's entire premise, executing on infrastructure defined in code.

1.1 What a visitor sees

A single page asking for a transaction hash. Paste one, and within a few seconds the page states whether that transaction exists on-chain, how many blocks have confirmed it, who sent it, who received it, and how much of which token moved. Four outcomes are possible, and three of them are refusals to overstate:

OutcomeWhat it meansWhy it is not just "valid / invalid"
AGREEDAll three providers independently returned the same facts. The payment is real and fully described.Agreement is the evidence, not one server's say-so.
HELDThe providers do not agree yet — typically a transaction seconds old that some nodes have seen and others have not.The honest answer when the chain itself has not settled. Impossible to produce locally.
UNKNOWN_TOKENThe transaction is real and the amount is known, but the token is not one this deployment can name.Refuses to label an arbitrary contract as "USDC". Shows the amount, withholds the name.
NOT_FOUNDNo such transaction.—

2Infrastructure as code — AWS CDK in Python

The infrastructure is one CDK app. It was originally scaffolded in TypeScript; that was corrected to Python, which is now the standard for infrastructure in this project (the engineering-standard document has been amended to match — it had carried the same error).

2.1 Entry point: refusing to do the dangerous thing quietly

app.py does almost nothing except guard two failure modes that are much worse when they are silent.

infra/deploy/cdk/app.pyCDK entry point
app = cdk.App()

# Both optional, and the default is no SSH at all: no open port and no key on the box.
#
# Ansible connects over SSM and the console connects through Session Manager, so an SSH rule
# protects nothing here while still being a rule that goes stale - a home address changes, and
# the entry then names a stranger's. Supply both of these together if you ever want SSH back.
ssh_cidr = app.node.try_get_context("sshCidr")
key_name = app.node.try_get_context("keyName")

# The one thing worth refusing outright. An address is a deliberate choice; the whole internet
# on port 22 is almost always a slip, and it is the slip this project should not make quietly.
if ssh_cidr and ssh_cidr.strip().endswith("/0"):
    raise SystemExit(
        f"Refusing sshCidr={ssh_cidr}: that is SSH open to the internet.\n"
        "Pass a single address, for example -c sshCidr=$(curl -s https://checkip.amazonaws.com)/32"
    )

# This stack looks up the default VPC, which CDK can only do for a named account and region.
# Without credentials the lookup fails several layers down as a jsii stack trace about a
# "context provider", which says nothing useful to the person who simply has not logged in yet.
account = os.environ.get("CDK_DEFAULT_ACCOUNT")
if not account:
    raise SystemExit(
        "No AWS account resolved, so the default-VPC lookup cannot run.\n"
        "Configure credentials and try again, for example:\n"
        "  aws configure                 # or\n"
        "  export AWS_PROFILE=<profile>  # for an SSO or named profile"
    )

The default is no SSH at all — no inbound port 22, and no key pair on the instance. This was not the starting position; it was arrived at deliberately after confirming that Ansible (over SSM) and the AWS console (over Session Manager) both work without it, which makes an open port 22 pure attack surface with no compensating use.

2.2 The stack

demo_stack.py is about 250 lines and creates: three ECR repositories, an S3 transfer bucket, a KMS key, a security group, an IAM role, one EC2 instance with user-data, and an Elastic IP. Each decision is recorded in the class docstring because each one differs from what the real platform will do.

infra/deploy/cdk/demo_stack.py — class docstringrationale
"""The demo's infrastructure.

The real platform is planned as CDK stacks split by blast radius - network, data, security,
edge, one per service, on EKS with RDS, MSK and KMS (infra/README.md). This is not that, and
is not trying to be: it is the demo, sized for a demo, written so the parts that matter later
are already expressed as code rather than clicked into a console.

Deliberate choices, each of which the real stack makes differently:

- **The default VPC is used, not a new one.** A private subnet needs a NAT gateway to pull
  images, which costs more per month than the instance. The box is public-subnet with a
  security group doing the work.
- **Postgres and Kafka run as containers, not RDS and MSK.** One box, one demo. The compose
  file keeps one database per service, so moving to RDS later is a connection string.
- **No load balancer.** Caddy terminates TLS on the box with Let's Encrypt, which is free and
  renews itself. An ALB with ACM is the production answer and costs about sixteen dollars a
  month to serve one page.
"""

Credential handling Credentials were never written to ~/.aws and never committed. 4Configuration management — Ansible over SSM

The division of labour is strict and worth stating before any detail. CDK creates infrastructure; Ansible configures the box and runs the application. Nothing is ever edited on the server — a change is made in git and the playbook runs again. The playbook is idempotent by construction, which is the entire point of it: it is not a bootstrap script that runs once, it is a description of what the box should look like, applied as often as you like.

4.1 What runs where

Ansible is agentless in the usual sense — there is no Ansible daemon on the box — but it is not contactless. Three machines are involved in a single ./play:

Also performs the final HTTPS gates. Docker, and AWS credentials in the environment. Nothing else — no Python version requirement, no pip installs.

4.2 How the connection actually works

This is the part that differs most from a conventional Ansible setup, and the part most worth understanding, because every quirk in the playbook descends from it. There is no SSH anywhere in the path.

Step by step, what one task does:

  1. Ansible resolves the host to an instance ID (not an IP) from the inventory.
  2. The community.aws.aws_ssm plugin opens a Session Manager session using your AWS credentials. The session-manager-plugin binary in the image does the websocket work.
  3. The module's Python code and any file it needs are uploaded to the S3 transfer bucket, because the Session Manager channel carries a terminal stream, not files.
  4. A command is sent over the session telling the box to fetch that object from S3 — which it can, because its instance role has read/write on the bucket — and execute it.
  5. Output returns over the session; larger results go back via S3 the same way.
Why this is the right trade for a public box No inbound port, no key material anywhere, no authorized_keys to rotate, and no bastion. Access is granted and revoked purely with IAM, and every session is recorded in CloudTrail. The security group for this deployment contains no SSH rule at all — and the deploy still works, which is the proof that the rule was never needed.

4.6 Variables, and the discipline around secrets

playbook.ymlvars

Everything is derived from playbook_dir, so the playbook works regardless of where it is invoked from, including from inside the container where the repository is mounted at /repo.

.env is parsed on the control node into a dictionary and never written anywhere except the box, at mode 0600:

playbook.ymlreading .env
- name: Read the deployment environment
  ansible.builtin.set_fact:
    deploy_env: "{{ lookup('ansible.builtin.file', env_file) | regex_findall('(?m)^([A-Z0-9_]+)=(.*)$') | items2dict(key_name=0, value_name=1) }}"
  no_log: true
no_log: true is load-bearing It appears on every task that touches a secret: reading .env, asserting over its keys, copying it to the box, rendering init.sql (which interpolates two passwords), and the ECR login. Without it, Ansible prints the task's arguments on failure — so the first time anything went wrong, the database passwords would be in the terminal scrollback and in any CI log.

4.8 Idempotency and the handler

Re-running the playbook on an unchanged repository produces changed=3 — tasks 17 and 18 (which cannot know whether they changed anything without doing the work) and nothing else. The copy tasks compare checksums and stay ok. That is what makes the playbook usable as a routine operation rather than a ceremony: it is how a provider URL was swapped three times in §7.2, each time by editing one line of .env and re-running.

playbook.ymlhandler
handlers:
  - name: Restart the stack
    ansible.builtin.command:
      cmd: docker compose up -d
      chdir: "{{ app_dir }}"

Only the config copies notify it. Compose already restarts containers whose image or environment changed; the handler exists for the case where a mounted file changed but nothing compose can see did — editing the Caddyfile, for instance, which is a bind mount.

4.9 The gates — verifying from outside

Both checks use delegate_to: localhost, so they run from your laptop against the public hostname rather than from the box against itself. A check performed on the server would pass even if DNS, the certificate, the security group or the proxy were wrong.

7.1 Why three providers, and what they are not

The most common misreading of this design is that the three providers are three blockchains. They are not. They are three separate companies' servers, each running a node that syncs the one Sepolia ledger. There is a single chain and a single canonical history; what differs is who is telling you about it.

Blockchains are not linked to one another Bitcoin, Ethereum and Tron are wholly independent ledgers — separate histories, separate validators, separate consensus rules, with nothing joining them at the protocol level. A transaction hash from Ethereum is not "not found" on Tron; it belongs to a different universe of record entirely. This is why providers are configured per chain, and why ProviderSet demands three for ETHEREUM and three for TRON rather than three in total — the configuration and the callout directly above. Bridges exist, but they are applications built on top of two chains watching each other, not a protocol-level link.

So if all three read the same ledger, why ask three? Because the provider is not the blockchain. It is a company's server with an API in front of it. The moment a verdict rests on asking one endpoint, there is a trusted third party in the path — precisely the thing this product exists to remove. Anyone able to compromise, coerce or intercept that one endpoint can report a payment as real when it is not. Asking one provider does not verify a payment; it verifies what one company says about a payment.

What the three actually defend against

FailureWhat it looks likeHow the quorum catches it
A provider liesCompromised, coerced, or an intercepted connection.The other two disagree, so no fact reaches the 2-of-3 threshold.
A provider is staleLagging the chain tip, serving a cache, or partially synced after a restart.Confirmation counts disagree.

Measured, not theoretical Queried at one instant from the deployed box, the three providers answered blocks 12211599, 12211600 and 12211600. That one-block spread is not a fault: blocks propagate across a gossip network, so brief disagreement about the tip is the normal condition, not the exceptional one.

The deepest reason: a recent block is genuinely uncertain

A block near the tip can be orphaned. A transaction with one confirmation sits in a block that may yet be replaced, which means a payment that "happened" can un-happen. Different nodes briefly holding different views is not malfunction — it is how distributed consensus works before settlement.

This is what HELD is for, and it is the outcome that most justified deploying at all. Locally it was unreachable: all three configured "providers" pointed at a single anvil node, so they could never disagree. The quorum logic was written, unit-tested, and had never once been exercised against a real disagreement. The first transaction submitted to the public deployment returned HELD.

Why two of three

  • One of three — no better than trusting a single company.
  • Three of three — any single outage or one-block lag blocks every answer; availability collapses, and §7.2 shows outages are routine.
  • Two of three — tolerates one failure while still requiring independent corroboration.

Worth stating precisely: this is not Byzantine fault tolerance, which needs 3f+1 participants and a different threat model. It is a pragmatic corroboration threshold whose guarantee is narrower and worth saying plainly — no single provider can determine the answer alone.

The honest limit of the quorum

Quorum and confirmations defend different things, and conflating them would overstate the claim. Quorum protects against provider-level failure — lying, lag, downtime. Confirmations protect against chain-level provisionality. Three providers reading the same chain can be unanimously right about a block that is later reorganised out; no amount of agreement helps there, only depth does. On post-Merge Ethereum a block is finalized after roughly two epochs (about 13 minutes), after which reversal would require slashing a third of all staked ETH. That is what finality.enabled-chains tracks.

What the product therefore claims Not "this payment is real", which no observer can honestly promise, but something narrower and defensible: three independent witnesses agree this transaction exists, with this much settlement behind it — and it names the amount only for a token it can actually identify. Every outcome other than AGREED is that sentence refusing to overstate itself.

9What this achieves, and what it does not

9.1 From a user's point of view

Someone who has been sent a payment and a transaction hash can, with no account and no software, paste that hash into a public web page and learn — within seconds, from three independent sources — whether the payment is real, how settled it is, and exactly what moved. The page will say "not yet" when the chain has not settled, and will refuse to name a token it cannot identify. That refusal is the product: a verification service that overstates its confidence is worse than none.

9.2 What it proves to the team

  • The three services genuinely interoperate outside a developer machine, including real OAuth2 client_credentials between payment and crypto.
  • The 2-of-3 quorum works against real, disagreeing providers — and HELD, which no local test could ever produce, was observed.
  • The whole environment is reproducible from this repository: ./cdk deploy then ./play, from any machine with Docker and credentials. No console clicking, no undocumented state.
  • The startup guards built months ago (KMS, screening mode, signing key) all fired correctly the first time they were outside local. They were not theatre.

10Where we are, and where we are going

10.1 Where we are

The demo is live on the public internet at checkychain.com.ng, served through Cloudflare, with the origin closed to everything except Cloudflare's published ranges. A real Sepolia transaction was verified through that path and settled AGREED at 6.1425 USDC with 3035 confirmations. §11 is the record of how it got there.

What exists today:

  • A CDK (Python) stack that provisions the whole environment reproducibly, with the toolchain containerised so no machine needs Node, Python, Ansible or the AWS CLI installed to operate it.
  • An idempotent Ansible playbook that configures the box over SSM with no SSH, ships the TLS keypair, and gates its own success on live HTTPS checks that identify our server rather than merely finding a 200.
  • A production compose topology with a single public ingress, real service-to-service auth, out-of-service migrations and pull-only registry access.
  • A real domain behind a real edge: Cloudflare DNS and proxy, Universal SSL to visitors, a pinned Cloudflare Origin CA certificate on the box, and a security group that makes the proxy mandatory rather than optional.
  • Backend services (auth, crypto, payment, notification) complete and heavily tested; the frontend at task 46 of its plan, which is why the deployed surface is one page rather than the product.
What the deployment proved that the test suite could not Three things only became observable here. HELD was unreachable locally, because all three configured providers pointed at one anvil node and could never disagree (§7.1). Two RPC providers that answered perfectly from a laptop failed from EC2 — one with a 403, one with a 429 that only a ten-request burst exposed (§7.2). And a bind-mounted configuration file that docker compose up -d silently ignores cost two apparently-successful deploys before being understood (§4.8). None of these is reachable by a unit test, and none was hypothetical.

10.2 The immediate next steps

  1. Rate-limit the public endpoint at the Cloudflare edge. This is now the only thing standing between a working demo and a bill: closing the origin (§11.5) made the edge the single place where such a limit can be enforced, and the limit itself is not yet in place.
  2. Move off unauthenticated public RPC — keyed endpoints, so a demo cannot be throttled into a 503 by a stranger's traffic.
  3. Recover the real client IP with Caddy's trusted_proxies, which every request now needs and nothing currently provides (§11.9).
  4. Fix the 503 copy so a verification failure does not mention invoices.
  5. Tag images by commit SHA and stop deploying latest.

10.3 The longer arc

The demo stack is explicitly not the production design, and its docstring says so. The planned platform splits into CDK stacks by blast radius — network, data, security, edge, one per service — running on EKS with RDS, MSK and KMS. The useful property of what was built here is that the contracts are already right: one database per service, migrations outside the services, pull-only image access, least-privilege IAM, a single public ingress with default-deny. Each of those survives the move; only the implementations change.

11.3 What a registrar controls, and what it does not

The nameserver change was saved at DomainKing, the client area showed the new values, and a confirmation email arrived — and for roughly an hour the .ng registry still delegated to dan1–dan4.host-ww.net. Nothing was broken; the two are simply different systems, and only one of them is authoritative.

the only query that answers the questiondig
dig +norecurse @ns3.nic.net.ng NS checkychain.com.ng

Both halves carry weight. @ns3.nic.net.ng asks the .ng registry's own nameserver, bypassing every resolver — delegation is a record the registry holds, and everyone else is repeating what they heard from it. +norecurse means answer from your own records, do not go asking anyone else; without it a server may return a cached or recursively fetched answer, which tells you nothing about what that server actually holds.

This is the check that kept the migration honest. The registrar's panel, the registrar's confirmation email and the registrar's support would all have said the change was made. Only the registry says whether it took effect, and for about 54 minutes the answer was no.

Four resolvers, not one Once the registry flipped, propagation was confirmed against Cloudflare (1.1.1.1), Google (8.8.8.8), Quad9 (9.9.9.9) and OpenDNS on four different networks. The registry can be correct while resolvers still serve a stale answer for the length of the TTL — 3600 seconds here. One resolver agreeing proves very little; four agreeing means the caches have turned over. The chain was then followed to the end: the apex resolved to 188.114.96.0, whois on that address returned CLOUDFLARENET-EU, and a real request came back with server: cloudflare and a cf-ray header naming the Amsterdam edge. Delegation being correct does not mean the proxy is serving; each link was measured separately.
DomainKing's revert email is a security notice, not a hold Shortly after the change, DomainKing emailed: "If you did not authorise this change, you can revert to the previous nameservers within 24 hours." It is tempting to read that as a 24-hour hold before the change is pushed. It is the opposite — the change is applied and the link is an undo. Clicking it would have reverted the migration. The email is worth keeping as the escape hatch and otherwise ignoring, exactly as it says.

11.4 The certificate, and why ACME had to go

This is the decision that silently breaks setups two months after they appear to work.

Caddy had been getting its certificate from Let's Encrypt over the HTTP-01 challenge, which requires Let's Encrypt to reach port 80 on the box. The moment Cloudflare proxies the hostname and the firewall admits only Cloudflare, that path no longer exists. Nothing fails at cutover: the existing certificate is still valid, the site serves perfectly, and every check passes. The failure arrives at the first renewal, roughly sixty days later, by which time nobody is looking at the deployment that caused it.

So the origin stopped doing ACME altogether and was given a Cloudflare Origin CA certificate instead — valid only between Cloudflare's edge and this box, covering the apex and *.checkychain.com.ng, and expiring in 2041. There is nothing to renew.

infra/deploy/config/CaddyfileTLS
{$PUBLIC_HOST} {
	# Cloudflare Origin CA, not Let's Encrypt. Caddy performs no ACME at all, which is the point:
	# once Cloudflare proxies this hostname and the security group only admits Cloudflare, nothing
	# can reach port 80 from the public internet, so an HTTP-01 renewal would fail - and it would
	# fail at the first RENEWAL, about sixty days after a cutover that looked perfect. This
	# certificate is valid only between Cloudflare's edge and this box, and expires in 2041.
	# Visitors are served Cloudflare's own public certificate, which Cloudflare renews.
	tls /etc/caddy/origin.pem /etc/caddy/origin.key

The keypair is validated locally before it is shipped, because a certificate and a key that do not belong together produce a Caddy that starts and then refuses every connection:

validating the pair without printing the keyopenssl
openssl x509 -in origin.pem -noout -subject -dates -ext subjectAltName
openssl x509 -in origin.pem -noout -pubkey | openssl md5   # must equal
openssl pkey  -in origin.key -pubout      | openssl md5   # this

Ansible then installs it at 0644 for the certificate and 0600 for the key, both root-owned — the caddy image runs as root so it reads both, and no other account on the host can read the key. The key task carries no_log: true so its contents cannot reach the play output, and both notify the Restart edge handler, because a bind-mounted file that changes is invisible to docker compose up -d (§4.8).

A wrong instruction, corrected by hitting it The sequence originally given was to create the Origin CA certificate while the nameservers propagated, on the grounds that it needed no propagation. That is false, and Cloudflare answered Failed to validate requested hostname *.checkychain.com.ng. Origin CA only issues for a zone in Active state, and a zone becomes Active only once Cloudflare sees the delegation. The certificate step cannot be parallelised with the wait; it depends on it.
The certificate a visitor sees is issued by Let's Encrypt Checked after cutover, the public certificate is CN=checkychain.com.ng issued by Let's Encrypt, not by Cloudflare. That is Cloudflare Universal SSL, which Cloudflare provisions and renews through Let's Encrypt as its CA; it expires in February 2027 and needs no attention. Worth recording only because the preceding paragraphs promise "Cloudflare's own certificate", and a reader checking in a browser would otherwise think something had gone wrong.

11.5 Closing the origin, and the trap inside it

With Cloudflare in front but ports 80 and 443 still open to 0.0.0.0/0, the proxy is optional. The origin address is not a secret — it sits in certificate transparency logs and in old DNS history — so anyone who looks it up can skip the rate limiting, the WAF and the caching by talking to the box directly. The firewall is what makes the edge mandatory rather than merely usual.

infra/deploy/cdk/demo_stack.pyingress
if edge == "cloudflare":
    for cidr in CLOUDFLARE_IPV4:
        security_group.add_ingress_rule(
            ec2.Peer.ipv4(cidr), ec2.Port.tcp(443), "HTTPS from Cloudflare"
        )
        security_group.add_ingress_rule(
            ec2.Peer.ipv4(cidr), ec2.Port.tcp(80), "HTTP from Cloudflare (redirect)"
        )
    for cidr in CLOUDFLARE_IPV6:
        ...

Fifteen IPv4 and seven IPv6 ranges, pinned in the source rather than fetched during synth — a synth that reaches the network behaves differently depending on when and where it runs, and cannot deploy while that endpoint is down. The cost is that the list goes stale, so the refresh command sits in a comment beside it. The list was verified rather than trusted: the edge addresses actually serving the site at the time (188.114.96.0 and 188.114.97.0) were both confirmed to fall inside 188.114.96.0/20. A published list that did not contain the address in use would be the wrong list.

A -c edge=public escape hatch retains the open-to-the-internet mode for a hostname with no proxy in front. That mode and the tls directive above are mutually exclusive, and both files say so: the firewall rules are precisely what stops an HTTP-01 challenge reaching port 80, so changing one without the other is the sixty-day failure described in §11.4.

A one-line cosmetic edit that would have destroyed the database The security group's description still read "Public demo: HTTP/HTTPS from anywhere", which had become false, so it was corrected to say Cloudflare only. The cdk diff for that one-line change reported: 
[~] AWS::EC2::SecurityGroup DemoSg  replace
 └─ [~] GroupDescription (requires replacement)
[~] AWS::EC2::Instance DemoInstance  may be replaced
 └─ [~] SecurityGroupIds (may cause replacement)
A security group's GroupDescription is immutable in AWS. Editing it replaces the group, which repoints the instance's SecurityGroupIds, which CloudFormation reports as a possible instance replacement — and a replaced instance is a new EBS volume, so the postgres-data volume and every receipt in it would have gone with it. The ingress rules themselves are perfectly mutable; the description was the only thing forcing replacement. It is therefore left stale on purpose, with a comment in the source saying why it must not be corrected, and the accurate description recorded above the rules instead. Caught by reading the diff rather than by deploying it, which is the entire argument for reading diffs.

Error 526 is the expected intermediate state, not a fault Between pointing the DNS record at the box and installing the origin certificate, the site returns Cloudflare's error code: 526 — invalid origin certificate. It is worth expecting, because it is also diagnostic: a 526 proves DNS reaches the right box and that Full (strict) is genuinely validating, which is two of the three things you wanted confirmed. It was seen here exactly once, and resolved by the step that was always going to resolve it.

11.8 Rebuilding, and a correction about what survives a teardown

The stack had been destroyed the previous day to stop it billing, and the rebuild took about thirteen minutes: four for cdk deploy, three to push images, six for Ansible. That is possible only because the built images still existed on the laptop.

ECR repositories do not survive cdk destroy It was stated during the teardown that the images would remain in ECR and the rebuild would therefore be quick. That was wrong: demo_stack.py sets empty_on_delete=True and RemovalPolicy.DESTROY on each repository — deliberately, so a teardown leaves nothing behind — and all three repositories went with the stack. The rebuild was fast for a different reason: the arm64 images were still in the local Docker cache and only needed re-pushing, with no Maven build. The practical consequence is a standing instruction between teardown and rebuild: do not run docker system prune, or a thirteen-minute rebuild becomes a forty-minute one.

11.9 What remains

  1. Rate limiting on POST /api/v1/verifications — dashboard work, and the reason the origin was closed. Ten requests per minute per IP, blocking for one minute, which is within the free tier's single-rule allowance. The endpoint costs three upstream RPC calls per request, so ten per minute is thirty RPC calls per minute — comfortably inside the free provider quotas whose limits are documented in §7.2.
  2. Recovering the real client IP. Every request now arrives from a Cloudflare address, so logs and any future per-IP logic see the proxy rather than the caller. Caddy needs a trusted_proxies directive carrying the same ranges as the security group. Deferred deliberately: it duplicates the pinned list, and the honest fix is to generate both from one source rather than maintain two.
  3. Refreshing the pinned ranges. Cloudflare changes them rarely but does change them. A stale list fails closed — legitimate edge traffic is refused — which is the safe direction, but it fails as an outage.
  4. The items §10.2 already names that this section did not touch: keyed RPC endpoints, the 503 copy that still mentions invoices, and tagging images by commit SHA instead of deploying latest.

It reads from AWS, writes two local files, and changes no infrastructure. It refuses to run at all if .env or the Origin CA pair is missing, rather than writing an inventory for a deploy that cannot possibly succeed.
