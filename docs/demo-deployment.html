1What this is

The platform is a multi-service payment-dispute system — auth, crypto, payment, notification and intelligence services, built over months against specs and heavily tested suites. None of that had ever run anywhere but a laptop. This exercise took the leanest slice that still proves the core claim — paste a transaction hash, get an independent on-chain verdict — and put it on the public internet with a real certificate.

The slice is deliberately thin. No sign-in, no merchant dashboard, no invoices. One page, one endpoint, three services behind it, and three independent blockchain providers voting on what is true. Everything else in the platform is present on the box but unroutable.

The one result that matters A real Sepolia transaction, submitted to the public URL, returned outcome: AGREED, existence: AGREED, 26 confirmations and "0.01 WETH" with both addresses — every fact agreed 2-of-3 by three separate companies' nodes. That is the product's entire premise, executing on infrastructure defined in code.

1.1 What a visitor sees

A single page asking for a transaction hash. Paste one, and within a few seconds the page states whether that transaction exists on-chain, how many blocks have confirmed it, who sent it, who received it, and how much of which token moved. Four outcomes are possible, and three of them are refusals to overstate:

OutcomeWhat it meansWhy it is not just "valid / invalid"
AGREEDAll three providers independently returned the same facts. The payment is real and fully described.Agreement is the evidence, not one server's say-so.
HELDThe providers do not agree yet — typically a transaction seconds old that some nodes have seen and others have not.The honest answer when the chain itself has not settled. Impossible to produce locally.
UNKNOWN_TOKENThe transaction is real and the amount is known, but the token is not one this deployment can name.Refuses to label an arbitrary contract as "USDC". Shows the amount, withholds the name.
NOT_FOUNDNo such transaction.—

2Infrastructure as code — AWS CDK in Python

The infrastructure is one CDK app. It was originally scaffolded in TypeScript; that was corrected to Python, which is now the standard for infrastructure in this project (the engineering-standard document has been amended to match — it had carried the same error).

2.1 Entry point: refusing to do the dangerous thing quietly

app.py does almost nothing except guard two failure modes that are much worse when they are silent.

infra/deploy/cdk/app.pyCDK entry point
app = cdk.App()

# Both optional, and the default is no SSH at all: no open port and no key on the box.
#
# Ansible connects over SSM and the console connects through Session Manager, so an SSH rule
# protects nothing here while still being a rule that goes stale - a home address changes, and
# the entry then names a stranger's. Supply both of these together if you ever want SSH back.
ssh_cidr = app.node.try_get_context("sshCidr")
key_name = app.node.try_get_context("keyName")

# The one thing worth refusing outright. An address is a deliberate choice; the whole internet
# on port 22 is almost always a slip, and it is the slip this project should not make quietly.
if ssh_cidr and ssh_cidr.strip().endswith("/0"):
    raise SystemExit(
        f"Refusing sshCidr={ssh_cidr}: that is SSH open to the internet.\n"
        "Pass a single address, for example -c sshCidr=$(curl -s https://checkip.amazonaws.com)/32"
    )

# This stack looks up the default VPC, which CDK can only do for a named account and region.
# Without credentials the lookup fails several layers down as a jsii stack trace about a
# "context provider", which says nothing useful to the person who simply has not logged in yet.
account = os.environ.get("CDK_DEFAULT_ACCOUNT")
if not account:
    raise SystemExit(
        "No AWS account resolved, so the default-VPC lookup cannot run.\n"
        "Configure credentials and try again, for example:\n"
        "  aws configure                 # or\n"
        "  export AWS_PROFILE=<profile>  # for an SSO or named profile"
    )

The default is no SSH at all — no inbound port 22, and no key pair on the instance. This was not the starting position; it was arrived at deliberately after confirming that Ansible (over SSM) and the AWS console (over Session Manager) both work without it, which makes an open port 22 pure attack surface with no compensating use.

2.2 The stack

demo_stack.py is about 250 lines and creates: three ECR repositories, an S3 transfer bucket, a KMS key, a security group, an IAM role, one EC2 instance with user-data, and an Elastic IP. Each decision is recorded in the class docstring because each one differs from what the real platform will do.

infra/deploy/cdk/demo_stack.py — class docstringrationale
"""The demo's infrastructure.

The real platform is planned as CDK stacks split by blast radius - network, data, security,
edge, one per service, on EKS with RDS, MSK and KMS (infra/README.md). This is not that, and
is not trying to be: it is the demo, sized for a demo, written so the parts that matter later
are already expressed as code rather than clicked into a console.

Deliberate choices, each of which the real stack makes differently:

- **The default VPC is used, not a new one.** A private subnet needs a NAT gateway to pull
  images, which costs more per month than the instance. The box is public-subnet with a
  security group doing the work.
- **Postgres and Kafka run as containers, not RDS and MSK.** One box, one demo. The compose
  file keeps one database per service, so moving to RDS later is a connection string.
- **No load balancer.** Caddy terminates TLS on the box with Let's Encrypt, which is free and
  renews itself. An ALB with ACM is the production answer and costs about sixteen dollars a
  month to serve one page.
"""

Credential handling Credentials were never written to ~/.aws and never committed. 4Configuration management — Ansible over SSM

The division of labour is strict and worth stating before any detail. CDK creates infrastructure; Ansible configures the box and runs the application. Nothing is ever edited on the server — a change is made in git and the playbook runs again. The playbook is idempotent by construction, which is the entire point of it: it is not a bootstrap script that runs once, it is a description of what the box should look like, applied as often as you like.

4.1 What runs where

Ansible is agentless in the usual sense — there is no Ansible daemon on the box — but it is not contactless. Three machines are involved in a single ./play:

Also performs the final HTTPS gates. Docker, and AWS credentials in the environment. Nothing else — no Python version requirement, no pip installs.

4.2 How the connection actually works

This is the part that differs most from a conventional Ansible setup, and the part most worth understanding, because every quirk in the playbook descends from it. There is no SSH anywhere in the path.

Step by step, what one task does:

  1. Ansible resolves the host to an instance ID (not an IP) from the inventory.
  2. The community.aws.aws_ssm plugin opens a Session Manager session using your AWS credentials. The session-manager-plugin binary in the image does the websocket work.
  3. The module's Python code and any file it needs are uploaded to the S3 transfer bucket, because the Session Manager channel carries a terminal stream, not files.
  4. A command is sent over the session telling the box to fetch that object from S3 — which it can, because its instance role has read/write on the bucket — and execute it.
  5. Output returns over the session; larger results go back via S3 the same way.
Why this is the right trade for a public box No inbound port, no key material anywhere, no authorized_keys to rotate, and no bastion. Access is granted and revoked purely with IAM, and every session is recorded in CloudTrail. The security group for this deployment contains no SSH rule at all — and the deploy still works, which is the proof that the rule was never needed.

4.6 Variables, and the discipline around secrets

Everything is derived from playbook_dir, so the playbook works regardless of where it is invoked from, including from inside the container where the repository is mounted at /repo.

.env is parsed on the control node into a dictionary and never written anywhere except the box, at mode 0600:

playbook.ymlreading .env
- name: Read the deployment environment
  ansible.builtin.set_fact:
    deploy_env: "{{ lookup('ansible.builtin.file', env_file) | regex_findall('(?m)^([A-Z0-9_]+)=(.*)$') | items2dict(key_name=0, value_name=1) }}"
  no_log: true
no_log: true is load-bearing It appears on every task that touches a secret: reading .env, asserting over its keys, copying it to the box, rendering init.sql (which interpolates two passwords), and the ECR login. Without it, Ansible prints the task's arguments on failure — so the first time anything went wrong, the database passwords would be in the terminal scrollback and in any CI log.

4.8 Idempotency and the handler

Re-running the playbook on an unchanged repository produces changed=3 — tasks 17 and 18 (which cannot know whether they changed anything without doing the work) and nothing else. The copy tasks compare checksums and stay ok. That is what makes the playbook usable as a routine operation rather than a ceremony: it is how a provider URL was swapped three times in §7.2, each time by editing one line of .env and re-running.

playbook.ymlhandler
handlers:
  - name: Restart the stack
    ansible.builtin.command:
      cmd: docker compose up -d
      chdir: "{{ app_dir }}"

Only the config copies notify it. Compose already restarts containers whose image or environment changed; the handler exists for the case where a mounted file changed but nothing compose can see did — editing the Caddyfile, for instance, which is a bind mount.

7.1 Why three providers, and what they are not

The most common misreading of this design is that the three providers are three blockchains. They are not. They are three separate companies' servers, each running a node that syncs the one Sepolia ledger. There is a single chain and a single canonical history; what differs is who is telling you about it.

Blockchains are not linked to one another Bitcoin, Ethereum and Tron are wholly independent ledgers — separate histories, separate validators, separate consensus rules, with nothing joining them at the protocol level. A transaction hash from Ethereum is not "not found" on Tron; it belongs to a different universe of record entirely. This is why providers are configured per chain, and why ProviderSet demands three for ETHEREUM and three for TRON rather than three in total — the configuration and the callout directly above. Bridges exist, but they are applications built on top of two chains watching each other, not a protocol-level link.

So if all three read the same ledger, why ask three? Because the provider is not the blockchain. It is a company's server with an API in front of it. The moment a verdict rests on asking one endpoint, there is a trusted third party in the path — precisely the thing this product exists to remove. Anyone able to compromise, coerce or intercept that one endpoint can report a payment as real when it is not. Asking one provider does not verify a payment; it verifies what one company says about a payment.

What the three actually defend against

FailureWhat it looks likeHow the quorum catches it
A provider liesCompromised, coerced, or an intercepted connection.The other two disagree, so no fact reaches the 2-of-3 threshold.
A provider is staleLagging the chain tip, serving a cache, or partially synced after a restart.Confirmation counts disagree.

Measured, not theoretical Queried at one instant from the deployed box, the three providers answered blocks 12211599, 12211600 and 12211600. That one-block spread is not a fault: blocks propagate across a gossip network, so brief disagreement about the tip is the normal condition, not the exceptional one.

The deepest reason: a recent block is genuinely uncertain

A block near the tip can be orphaned. A transaction with one confirmation sits in a block that may yet be replaced, which means a payment that "happened" can un-happen. Different nodes briefly holding different views is not malfunction — it is how distributed consensus works before settlement.

This is what HELD is for, and it is the outcome that most justified deploying at all. Locally it was unreachable: all three configured "providers" pointed at a single anvil node, so they could never disagree. The quorum logic was written, unit-tested, and had never once been exercised against a real disagreement. The first transaction submitted to the public deployment returned HELD.

Why two of three

  • One of three — no better than trusting a single company.
  • Three of three — any single outage or one-block lag blocks every answer; availability collapses, and §7.2 shows outages are routine.
  • Two of three — tolerates one failure while still requiring independent corroboration.

Worth stating precisely: this is not Byzantine fault tolerance, which needs 3f+1 participants and a different threat model. It is a pragmatic corroboration threshold whose guarantee is narrower and worth saying plainly — no single provider can determine the answer alone.

The honest limit of the quorum

Quorum and confirmations defend different things, and conflating them would overstate the claim. Quorum protects against provider-level failure — lying, lag, downtime. Confirmations protect against chain-level provisionality. Three providers reading the same chain can be unanimously right about a block that is later reorganised out; no amount of agreement helps there, only depth does. On post-Merge Ethereum a block is finalized after roughly two epochs (about 13 minutes), after which reversal would require slashing a third of all staked ETH. That is what finality.enabled-chains tracks.

What the product therefore claims Not "this payment is real", which no observer can honestly promise, but something narrower and defensible: three independent witnesses agree this transaction exists, with this much settlement behind it — and it names the amount only for a token it can actually identify. Every outcome other than AGREED is that sentence refusing to overstate itself.

9What this achieves, and what it does not

9.1 From a user's point of view

Someone who has been sent a payment and a transaction hash can, with no account and no software, paste that hash into a public web page and learn — within seconds, from three independent sources — whether the payment is real, how settled it is, and exactly what moved. The page will say "not yet" when the chain has not settled, and will refuse to name a token it cannot identify. That refusal is the product: a verification service that overstates its confidence is worse than none.

9.2 What it proves to the team

  • The three services genuinely interoperate outside a developer machine, including real OAuth2 client_credentials between payment and crypto.
  • The 2-of-3 quorum works against real, disagreeing providers — and HELD, which no local test could ever produce, was observed.
  • The whole environment is reproducible from this repository: ./cdk deploy then ./play, from any machine with Docker and credentials. No console clicking, no undocumented state.
  • The startup guards built months ago (KMS, screening mode, signing key) all fired correctly the first time they were outside local. They were not theatre.

11.2 Three findings that change the plan

1 · Moving nameservers can silently destroy email checky.pro runs Google Workspace. Changing the nameservers to Cloudflare means every record must exist at Cloudflare before the switch — all five MX records and both TXT records included. Cloudflare's import scan is good but not guaranteed to be complete, and the failure mode is brutal: mail stops being delivered, with no error anyone sees until someone mentions they have not heard back. This risk is entirely absent from Route A below.
2 · app.checky.pro is already reserved — and already broken It points at a Bubble.io app that answers domain_not_supported. That hostname is also the SPA's registered OAuth redirect host in the auth-service seed data (https://app.checky.pro/auth/callback). So it is the frontend's name, it is currently dead, and the demo must not take it. Use verify.checky.pro.
3 · Two free hardening wins while you are in there There is no DMARC record and no CAA record. Neither is required for this deployment, but both are a few minutes of work in the same DNS panel, and DMARC in particular is worth having on a domain whose entire business is telling people what is genuine. Start with v=DMARC1; p=none; rua=mailto:… — report-only, so it cannot bounce legitimate mail — and tighten to p=quarantine once the reports look clean. Also confirm DKIM is switched on in the Google Admin console: nothing is published at the usual google._domainkey selector.

Recommendation: do A now, B deliberately and separately. Route A takes about ten minutes and gets the demo onto verify.checky.pro with nothing else at stake. Route B is worth doing — the rate limiting in particular is the only real answer to an unauthenticated endpoint that costs three upstream RPC calls per request — but it is a DNS migration of a live domain, and it deserves its own change window rather than being bundled into a demo deploy.

Why there is no middle option on the free plan Cloudflare can proxy a single hostname while another provider keeps the zone — "partial" or "CNAME setup" — but that is a Business-plan feature (around USD 200/month). On Free and Pro, proxying anything means Cloudflare must be authoritative for the whole zone. That is precisely why Route B is all-or-nothing and why Route A exists.

Step 4 · The certificate decision

This is the step most people get wrong, and it fails sixty days later Caddy currently uses the HTTP-01 challenge, which needs Let's Encrypt to reach port 80 on the origin. Once Cloudflare proxies the hostname, the origin is no longer directly addressable and HTTP-01 renewal becomes unreliable. Everything keeps working at switch-over — the break happens at the first renewal, about two months later, which is the worst possible time to discover it.
OptionHow it worksTrade-off
Cloudflare Origin CA recommended Cloudflare issues a certificate (up to 15 years) valid only between its edge and your origin. Caddy serves it via an explicit tls directive and stops doing ACME entirely. Visitors see Cloudflare's own public certificate. Nothing to renew, nothing to break. Requires SSL mode Full (strict).
DNS-01 with an API token Caddy keeps Let's Encrypt but proves control via a DNS TXT record, so the origin need not be reachable. Needs a custom Caddy image — the Cloudflare DNS module is not in the standard build — plus a scoped API token stored on the box.

Step 7 · Lock the origin to Cloudflare

With the proxy on, anyone who learns the Elastic IP can bypass Cloudflare and hit the box directly, defeating the WAF and the rate limit entirely. Accept 80 and 443 only from Cloudflare.

demo_stack.py — replacing the two any-ipv4 rulesCDK
# Cloudflare's published edge ranges: https://www.cloudflare.com/ips-v4
# Pass them in at synth time rather than pasting a list that will silently go stale:
#   ./cdk deploy -c cloudflareIpsV4="$(curl -s https://www.cloudflare.com/ips-v4)"
# Treat the fetched list as data: every entry must parse as a CIDR before it becomes a rule.
cloudflare_v4 = app.node.try_get_context("cloudflareIpsV4")

if cloudflare_v4:
    for cidr in [c.strip() for c in cloudflare_v4.replace(",", "\n").split() if c.strip()]:
        security_group.add_ingress_rule(ec2.Peer.ipv4(cidr), ec2.Port.tcp(443), "Cloudflare edge")
        security_group.add_ingress_rule(ec2.Peer.ipv4(cidr), ec2.Port.tcp(80), "Cloudflare edge")
else:
    # Fallback: open, as today. Correct only while the hostname is unproxied (Route A).
    security_group.add_ingress_rule(ec2.Peer.any_ipv4(), ec2.Port.tcp(80), "HTTP (ACME + redirect)")
    security_group.add_ingress_rule(ec2.Peer.any_ipv4(), ec2.Port.tcp(443), "HTTPS")
A sturdier alternative: Cloudflare Tunnel Running cloudflared as one more container removes inbound ports altogether — the box dials out and nothing needs to be open, so there is no IP allowlist to go stale and no origin address to leak. It costs one container and a tunnel token, and it still requires the zone to be on Cloudflare. If Route B is happening anyway, this is the better endpoint.

12.2 Access without SSH

  • Console: EC2 → Connect → Session Manager. The session lands as ssm-user.
  • sudo cd /home/ec2-user cannot work — cd is a shell builtin, not a program. Use sudo -i or sudo su - ec2-user. The home directory is mode 700, which is why ssm-user cannot enter it.
  • The application is at /opt/checky. Do not edit it: the playbook overwrites it on the next run. Change the repository instead.
  • The Java images contain no shell, so docker compose exec payment sh fails by design. Use docker compose logs.
