Crypto Service Branch Review

Board summary: comparing spec/service-specs-and-ai-framework and feat/crypto-quorum-and-evm-adapter

Executive Summary

The repository currently contains two independent Crypto Service implementations. One was delivered by the spec branch as a full, design-compliant stack; the other was delivered by the feat branch as a minimal, runnable slice. They are not interchangeable, and they do not safely compose in main today.

Recommendation Adopt the spec stack as the project’s Crypto Service implementation. It is the only stack that satisfies the architectural locked decisions in spec/crypto-service/design.md and agents.md. Selected ideas from the feat branch should be ported into it, not the other way around.
Current risk in main Because both stacks were merged, main now has incompatible types, duplicate scheduled watchers, and a broken hybrid. The service does not compile cleanly and should not be deployed until one stack is selected and the other is removed.

Project Landscape — What Exists in main

The approved architecture calls for four backend services, shared libraries, contracts, a frontend, and infrastructure. From the main branch today, only the Auth Service is fully implemented; the Crypto Service is partially built but internally conflicted; everything else is either specified only or not yet started.

The Two Crypto Service Stacks

1. Spec stack — com.themistra.crypto.adapter

A comprehensive implementation derived from spec/crypto-service/design.md.

  • Push/subscription-based adapters
  • Verbatim observation log + S3 snapshots
  • Reorg-safe cursors and chain.tx.reorged
  • Per-chain finality policies
  • Attestation + KMS signing
  • Fail-closed OFAC screening
  • Signed token allowlist
  • Transactional outbox for Kafka
  • Multi-replica watcher sharding with ShedLock

2. Feat stack — com.themistra.crypto.chain

A minimal runnable path: register a watch, discover a payment, verify it by quorum, publish an event.

  • Pull/log-scan-based EVM adapter (eth_getLogs)
  • Virtual-thread provider fan-out
  • Watch registration with caller-reference idempotency
  • Scheduled scan watcher
  • Local-dev UI for watches
  • Explicitly omits: reorg handling, observation log, provider-lag weighting, work sharding, attestation, screening, token allowlist, outbox

Overlap & Discrepancy

Overlap

  • Both implement per-provider chain adapters behind a common interface.
  • Both enforce a 2-of-3 quorum across independent providers.
  • Both register watches and attempt to detect incoming payments.
  • Both keep money exact in base units (spec uses BigDecimal; feat uses BigInteger).

The only file both PRs touched is pom.xml. The real overlap is in package names and class names, which is why the current code is fragile.

Discrepancy

Structural incompatibility in main
  • ProviderAnswer collision: spec expects a generic ProviderAnswer<T> with provider()/value(); feat supplies a non-generic record with providerLabel/observation/failure. This breaks QuorumDecisionService, HeldFactAlerter, and Watcher.
  • Watch entity mismatch: WatcherRegistry (spec) calls WatchStatus.REGISTERED, watch.watchId(), and watch.chain(); the current Watch entity (feat) has different fields/accessors and a different enum.
  • Duplicate scheduled watchers: WatcherRegistry.reconcile() and WatcherService.checkActiveWatches() are both @Scheduled; if both run, they compete.
  • Completeness gap: the feat stack lacks observation logs, reorg handling, attestation, screening, token allowlist, and transactional outbox — all locked requirements.

Recommendation

Pick the spec stack The spec/service-specs-and-ai-framework Crypto Service is the only implementation that can satisfy the platform’s design, security, and compliance requirements. The feat branch is a useful proof-of-concept and a source of implementation ideas, but it is not a production-grade Crypto Service.

Why the spec stack wins

  • It is the only stack aligned with the locked decisions in spec/crypto-service/agents.md and design.md.
  • It provides the internal API (POST /internal/v1/watches, POST /internal/v1/attest, verification-keys endpoint) that the Payment Service depends on.
  • It includes the audit and compliance controls the platform needs: verbatim observation log, reorg handling, fail-closed screening, and KMS-only signing.
  • It is explicitly described as the project’s “single largest correctness risk”; choosing the smaller stack would knowingly accept that risk without mitigation.

Guideline: Porting Novel Ideas from Feat into Spec

Although the feat stack should not replace the spec stack, it contains several ideas that can strengthen the spec stack once the underlying models are aligned.

Novel idea from feat Where it helps the spec stack Porting approach
EVM log-scan discovery
findIncomingTransfers via eth_getLogs		 The spec stack’s watcher must discover candidate transactions for a watched address. A polling/log-scan adapter is simpler to operate than persistent websocket subscriptions. Implement a polling ChainAdapter (or a subscription adapter backed by periodic log scans) that returns observations through the existing ObservationSink. Keep the verbatim observation log and quorum flow unchanged.
CAIP-2 chain identifiers
ChainId namespace + reference		 The spec Chain enum only supports Ethereum and Tron. CAIP-2 identifiers are chain-agnostic and align with cross-chain standards. Replace or augment Chain with a CAIP-2-based value object. Update finality policies and adapter registries to key off it. Keep the launch scope to Ethereum/Tron until design approval.
Virtual-thread provider fan-out
QuorumReader with Executors.newVirtualThreadPerTaskExecutor()		 The spec stack queries providers but currently structures the call path differently. Concurrent virtual-thread queries reduce latency and improve isolation. Introduce a provider-query orchestrator inside the spec stack that fans out over virtual threads, records each answer verbatim into the observation log, and then hands normalized facts to QuorumEvaluator.
Provider-answer classification
saw / absent / failed		 The spec stack needs to distinguish “provider did not see the tx” from “provider could not answer.” That distinction is needed for correct quorum and health tracking. Adopt the classification pattern when recording observations. Ensure the observation log stores the raw response plus the classification, and that QuorumEvaluator treats absence as a first-class answer.
Address normalization
ChainAddress.normalise		 Address validation and normalization are required by the spec (EIP-55, Base58Check) but the feat implementation is concrete and tested. Port the normalization rules into the spec stack’s token/AddressValidator and use them at watch-registration and adapter boundaries.
Caller-reference idempotency
callerReference field on Watch		 The spec API accepts an invoiceUuid; callers need safe retry semantics. Add a caller-reference / idempotency key to the spec watch model and return the existing watch when the same reference is reused with identical terms.
Readable-amount dev UI
Decimal formatting in DevWatchController		 Developers and operators need human-readable amounts in local tools without changing wire-format behavior. Port the UI formatting into the spec stack’s dev controller, keeping base units authoritative on the wire.
Local-dev explorer
DevExplorerController, DevSampleService		 The spec stack needs local observability to verify the full pipeline end-to-end. Adapt the dev controllers to drive the spec adapter/quorum/watch path. Ensure dev endpoints are @Profile("local") and never reachable in production.

Suggested porting sequence

  1. Choose a single chain-identity model. Recommend CAIP-2 records, mapped to the spec’s finality-policy and adapter registry.
  2. Reconcile the watch data model. Keep the spec design’s fields/statuses but add caller-reference idempotency and address normalization from feat.
  3. Reconcile the quorum layer. Keep spec’s QuorumEvaluator pure logic; replace or wrap provider query execution with feat-style virtual-thread fan-out and saw/absent/failed classification, feeding the verbatim observation log.
  4. Implement chain adapters consistently. Provide a polling/log-scan EVM adapter and a subscription-based adapter behind the same spec ChainAdapter interface.
  5. Remove the duplicate scheduled watcher. Keep the spec WatcherRegistry and remove/disable WatcherService.
  6. Restore missing modules. Ensure observation log, reorg detector, screening client, token allowlist, attest/KMS path, and transactional outbox are wired and tested.
  7. Port the dev UI. Move the readable-amount formatting and local explorer onto the spec stack’s dev endpoints.
  8. Make the service compile and pass tests. Fix dependency versions and module boundaries.
