## 1 · Architecture summary

A Vite + React + TypeScript single-page application, served under `/app` and reached only through a Caddy edge that
is the single origin (**L9**). There is no persistence layer, no event bus and no outbox in this package: the
analogues are **browser storage**, **the generated HTTP client**, and **the service worker**.

- **Modules.** `src/app` (shell, route table, mount), `src/auth` (the OIDC client: PKCE, authorize request,
  sign-in and callback screens, the nonce decision, the exchange seam), `src/api` (the generated client's wiring,
  the per-tab session boundary, cross-tab renewal, the rate-limit notice), `src/pwa` (hand-written service worker,
  navigation denylist, request policy), `src/i18n` (the string catalogue).
- **Persistence.** `sessionStorage` only, and only the **L16** carve-out: `state`, `nonce`, `code_verifier` and the
  post-login return target, single-use and deleted at callback (task 23). Three of those four are written by
  `authorizeRequest.ts:81-83`. **No token is ever stored** — tasks 21 and 22 own that property.
- **Transport.** Every backend call goes through `@themistra/api-client` (**L6**), a workspace package at
  `libs/ts/api-client`. `src/index.ts` is its only hand-written file: `createAuthClient()` is an `openapi-fetch`
  client with `baseUrl: ''`, so every path is relative and the edge routes it (L9, L10 — no base URL, no env key).
  `src/generated/auth.ts` is generated by `openapi-typescript` from `contracts/api/auth.yaml` and must not be
  hand-edited; CI regenerates and fails on drift (`contracts/README.md`, the package README).
- **Security.** The SPA is a **public** OIDC client, authorization code with PKCE, no client secret
  (`agents.md:19-21`). The edge maps `/oauth2/*`, `/login`, `/connect/*`, `/userinfo`, `/accounts*`, `/admin*`,
  `/api-keys*` to `auth:8080` and `/app*` to the dev server (`infra/local/edge/Caddyfile:12-28`), so the SAS
  endpoints really are same-origin. `.oxlintrc.json` bans `fetch` and `XMLHttpRequest` as globals **and** as
  properties of seven window aliases, each with the message "Call the backend through @themistra/api-client (L6)."

## 3 · Established patterns to follow

- **Generated client only (L6).** `design.md:38` — every backend call goes through `libs/ts/api-client`, generated
  from `contracts/api/*.yaml`, with exactly one named exception (the notification stream, R59/O7). The ban is
  enforced three ways: the lint config, the test `lintRejectsHandWrittenBackendFetch`, and `generatedClientCompiles`.
- **Nothing configured, everything derived.** No absolute address, no `import.meta.env` read in `src/auth`;
  `authorizeRequest.ts` builds the redirect URI from the route table and the page's own origin. Suites scan for
  both. `vite.config.ts` pins `envPrefix: ['VITE_']` and a test reads that line.
- **Seams that reject rather than pretend.** `codeExchange.ts` throws instead of resolving a fabricated token, so
  no check is ever proven against a value that will never occur.
- **Published constants, not copied literals.** The three storage keys are exported so every reader names the same
  constant; a source scan forbids spelling `themistra.auth.` by hand.
- **One closure for one outcome (L4).** Four different faults on the callback share one `discard`, so they cannot
  drift apart in copy, path or history action.
- **Catalogue-only strings (L11).** `src/i18n/catalogue.ts`; `signIn.discarded` is the neutral failure copy, and
  T19's suite pins both key sets exactly so a new string cannot be added unnoticed.
- **Doc comments carry the reasoning, including the rejected alternative.** This is the house style in `src/auth`
  and `src/api`; it is what made T19's reviews cheap.
- **Error handling.** There is **no error boundary anywhere in production source**. An uncaught throw blanks the
  page, which is why every storage read is wrapped and why the nonce decision is documented as never throwing.

## 4 · Testing conventions

- **Vitest 5.0.5 + jsdom 30.1.3**, one config (`vite.config.ts`). No Testcontainers, no ArchUnit, no fixed `Clock` —
  the counterparts are `vi.spyOn(Storage.prototype, …)`, `vi.doMock` for module seams, and `createMemoryRouter`
  over the **real** route table.
- **Install and run with `npx -y pnpm@12.14.0`.** A bare `pnpm` is not on this host.
- **One named test per task**, `package.md` §8, file name = test name.
- **Two layers where a decision has a wiring**: the pure function directly for the shape matrix, and through the
  mounted route table for the outcome — because T19's phase 6 found that a test double resolving the wrong shape
  silently defuses the check it was meant to exercise.
- **Every block carries a control** proving its assertion is *reached*, not merely satisfied; every source scan
  carries a synthetic violation proving the scan can fail.
- **Mutation testing** by a scratchpad harness that reverts with `git checkout --`, so **tests must be committed
  before any mutant runs**. T19 closed at 19 of 19 killed.
- **`vi.spyOn(globalThis, 'fetch')` is explicitly allowed** by the L6 lint test's ALLOWED table
  (`lintRejectsHandWrittenBackendFetch.test.ts:58`), which is how a test can observe what the generated client
  actually puts on the wire.
- **One known environmental failure**, and it must stay the only one: `lintRejectsHandWrittenBackendFetch` **AC4**
  expects the summary line `Found 0 warnings and 0 errors` and this host's `oxlint@1.87.0` prints nothing. **AC2**
  of the same file is a *different* fault (`spawn pnpm ENOENT`, passing under the `npx` recipe). The two have been
  conflated repeatedly in review; they are distinct.

## 5 · Known gaps and unknowns

1. **`/oauth2/token` is in no contract, and L6 requires one.** `contracts/api/auth.yaml:4-7` states that SAS's
   protocol endpoints "are governed by SAS itself and are **intentionally not documented here**", and `design.md`
   agrees that OIDC endpoints are SAS-owned. Meanwhile L6 says every backend call goes through a client generated
   from `contracts/api/*.yaml` — a **glob**, not `auth.yaml` alone — and the generator script names only
   `auth.yaml`. So the rule is satisfiable in principle by a second contract file and a second generated client,
   but `contracts/` "requires CODEOWNERS review" and changes there "trigger CI for every consumer". **This is
   OQ-5, carried from T19, and it is now T20's to resolve. I will not decide it in this phase.** Facts that bear on
   it, so Phase 2 does not have to rediscover them: `openapi-fetch@0.17.0` supports a `bodySerializer` both
   globally and per request (`dist/index.d.ts:13-14,115`), so a form-encoded body is expressible through a
   generated client; and the lint ban is on `fetch`/`XMLHttpRequest`, not on the token endpoint as such.
2. **There is no composition root.** `createAuthApi` and `createSessionBoundary` exist and are tested, but **nothing
   outside tests calls either** — `mountShell.tsx` builds i18n, the shell and the router and nothing else. Their doc
   comments say "production wiring passes…", and that wiring does not exist yet. Where a token store would be
   created, and by whom, is undecided; task 21 is the obvious owner but no task statement says so. **I do not know**
   which task is meant to build it.
3. **`redirectUri()` is private** in `authorizeRequest.ts`. The token request must send the *same* value the
   authorize request sent, or SAS refuses the exchange. Publishing it versus deriving it twice is a Phase 2/5
   decision; duplicating it would be the kind of second copy this package already regrets once
   (`segmentPrefixPattern`, noted in `apiRequestPolicy.ts:52`).
4. **The task name promises more than the task statement.** The named test is
   `callbackValidatesNonceAndKeepsAccessTokenInMemory`, but holding the token in memory is **task 21** and proving
   it reaches no storage is **task 22**. The split between what T20's test must assert and what it must leave
   failing or absent is a real boundary question for Phase 1/2.
5. **Two documented facts are measured FALSE**, neither T20's to fix but both nearby: `contracts/api/token-claims.md`
   places email and name in the `id_token` or at `/userinfo`, where **neither** appears (`/userinfo` returns only
   `{"sub"}`); and discovery advertises `scopes_supported: ["openid"]` for a three-scope client. Owner:
   `contracts/`.
6. **`refresh_token`'s absence is pinned by a comment**, `codeExchange.ts:19-25`, not by a test. Kimi's I5 from T19
   carried this here explicitly: T20 performs the real exchange and is the first task able to assert it.
7. **TanStack Query and Zustand are named in L13 and `agents.md:10` but are not installed** —
   `frontend/package.json` lists neither. Nothing in T20 obviously needs them; noted so it is not mistaken for an
   omission.
8. **The suite total is asserted in prose, not in CI** (819 today), and the `oxlint` AC4 failure has never been
   confirmed on CI. T18's Gap 6 is still open. This remains the one claim in the package resting on a single host.
9. **What happens to the visitor on a failed exchange is currently T19's answer, not a decided one.** T19 routes a
   rejection to `discard`, returning the visitor to the sign-in start with neutral copy, and its own comment says
   "Task 20 may route it somewhere more specific." Whether a `400 invalid_grant` should be distinguishable from a
   network failure — it must not be, by L4, as far as the visitor is concerned — is settled; whether anything else
   changes is open.
