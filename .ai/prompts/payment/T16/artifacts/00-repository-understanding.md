# payment · T16 · Phase 0 — Repository Understanding

Artifact: `.ai/prompts/payment/T16/artifacts/00-repository-understanding.md`

## 1. Architecture summary

`payment-service` (`services/payment`, package `com.themistra.payment`) is package-by-feature:
`invoice`, `payment`, `verification`, `consumer`, `events`, and `common` (shared plumbing). T15
just closed the "Crypto client" task (`CryptoClient.attest(...)`, the L3 ArchUnit ban). This task
(T16) opens the next sub-group within "Attestation, receipts, and ledger" (tasks 15–21):
computing the canonical digest that gets signed. Nothing in `receipt/`, `receipt/ledger/`, or
`attestation/` (per `design.md`'s own module diagram) has been built yet — T16 is the first.

## 2. Existing code this task touches

**Does not exist yet anywhere in this codebase (all net new):**
- `CanonicalJson` — no canonical-JSON serializer exists in `payment-service`, and a
  cross-service search (`grep -rl CanonicalJson services/*/src`) confirms no sibling service has
  one either — a wholly new utility, not adapted from an existing precedent.
- `ReceiptDigest` — no class of this name or shape exists.
- `Receipt`/`ReceiptRepository` entity — confirmed NOT yet built (per `design.md`'s own module
  diagram, `receipt/Receipt.java` is listed but belongs to task 17's own scope, not this one).
  **This means `ReceiptDigest`'s own method cannot take a `Receipt` entity as a parameter — it
  does not exist to pass.**
- A SHA-256 hashing utility specific to this module — `auth-service` has one
  (`auth.common.Hashing.sha256(String)`, `MessageDigest("SHA-256")` + `HexFormat`), but
  `agents.md`'s own platform rule ("Services depend only on `libs/` and `contracts/` — never on
  another service's source") forbids importing it directly; the pattern itself (not the class)
  is a reusable precedent to mirror.

**Already exists, read-only for this task (the fields `design.md` O4's own canonical payload
draws from):**
- `Invoice` (`invoice/Invoice.java`) — `merchantAccountUuid` (`UUID`), `chain` (`String`),
  `tokenContractAddress` (`String`), `tokenDecimals` (`short`), `amount` (`BigDecimal`),
  `payToAddress` (`String`), `invoiceUuid` (`UUID`).
- `Payment` (`payment/Payment.java`) — `paymentUuid` (`UUID`), `chain`, `txHash`, `fromAddress`
  (nullable `String`), `tokenContractAddress`, `amount` (`BigDecimal`), `finalizedAt` (`Instant`).
- **`receiptUuid`** — O4's own payload includes it, but no `Receipt` entity exists to read it
  from yet. It must be generated by this flow's own caller (T17, at the moment a receipt is
  first created) and passed in as a plain `UUID` parameter — mirrors `Invoice.create`/
  `Payment.createSeen`'s own existing pattern of generating a fresh `UUID.randomUUID()` for a new
  row's own public identifier.
- `ledger_entries.payload` (JSONB, `design.md` design-schema section) — the second real consumer
  of the same `CanonicalJson` utility this task builds (task 19, `LedgerService`), confirming the
  utility must stay genuinely generic (nested maps/lists, not hand-tuned to exactly O4's own flat
  12-field shape) even though both of this task's own two known real-world payloads happen to be
  flat today.

## 3. Established patterns to follow

- **Utility class shape.** No existing `payment-service` utility class (static-method-only,
  private constructor) exists yet to mirror directly within this service, but the cross-service
  convention is clear from `auth-service`'s `Hashing` (`public final class`, private no-arg
  constructor, `static` methods) — the same shape fits `CanonicalJson`.
- **Money/precision.** `agents.md`: money is `NUMERIC`/`BigDecimal`, and on the wire "decimal
  strings, never JSON numbers." `design.md` O4's own canonical payload shows `amount` as a
  **string** (`"<decimal string, base units>"`), not a JSON number — `CanonicalJson.serialize`
  must not silently coerce a `BigDecimal` value into a bare numeric JSON token; the caller
  (`ReceiptDigest`) is responsible for passing `amount.toPlainString()` into the map, matching
  every existing wire-DTO's own identical convention (`RegisterWatchRequest`, `AttestRequest`).
- **Time.** `agents.md`: no `java.util.Date`; `java.time` with an injectable `Clock` where a
  class generates its own timestamp. `ReceiptDigest` itself has no reason to call `Clock.now()`
  — `finalizedAt` is always caller-supplied (read from `Payment.getFinalizedAt()`), mirroring
  `CryptoClient.attest`'s own "trust the caller" stance for its own `Instant`-bearing fields.
- **Hex encoding.** `HexFormat.of().formatHex(...)` (confirmed via `auth-service`'s own
  `Hashing` — not reinventing a hand-rolled hex loop).

## 4. Testing conventions

- **Unit only, no Spring context** — `CanonicalJson`/`ReceiptDigest` are pure functions over
  plain Java types; no Testcontainers, no Kafka, no DB involvement at all, mirroring
  `CryptoClientTest`'s own "unit, real local objects, no Spring context" precedent for a
  similarly stateless/pure class.
- **Determinism is the core property to test.** The exact same logical input, with keys
  presented in different insertion orders, must produce byte-identical output — this is the one
  property that gives "sorted keys" its entire reason to exist, and the most important thing a
  test suite for this task must prove directly, not just assert against one fixed example.

## 5. Known gaps / unknowns

**Known, not a gap — resolved by direct reasoning above:** `receiptUuid` has no source entity to
read from yet; it is caller-generated. Not escalating this as an open question — it is exactly
the same shape as every other `UUID.randomUUID()`-at-creation pattern already established by
`Invoice.create`/`Payment.createSeen`, just one step removed (T17 generates it, passes it in).

**Genuine unknown for Phase 1/2 to resolve:** `design.md` O4's own canonical payload shows
`fromAddress` as `"<address|null>"` — explicitly nullable. `CanonicalJson.serialize`'s own task
text says "no key omitted" — but does NOT say how a `null` value is represented in the
canonical JSON output (as a literal JSON `null`, or should the key be present with an empty
string, or should `null` values be the one case where the key IS allowed to be omitted, directly
contradicting "no key omitted" read literally for a deliberately-absent field?). I do not know
which the task intends. This directly affects the hash's own determinism (whether an SHA-256
over `"fromAddress":null` and the same payload with a different omission convention could ever
collide/diverge for the same logical payment) and needs a Phase 2 decision, not a silent
assumption.

**Genuine unknown, lower stakes:** no precedent exists anywhere in this codebase for
canonicalizing a nested `Map`/`List` value (today's two known real payloads — O4's receipt
payload and the ledger entry payload — both appear to be flat). Whether `CanonicalJson` needs to
recursively canonicalize nested structures now (for genuine future-proofing, since its own
signature is declared generically as `Map<String,Object>` with no flatness constraint) or can
defer that to whenever a real nested payload actually shows up is a Phase 2 design question, not
resolved by anything in the spec package itself.
