## Principal-engineer review

**(1) Is the task fully complete?** Yes. Both named tests (`shouldDedupeDuplicateChainEventsByEventKey`, `shouldIgnoreOutOfOrderOrStaleChainEvents`) exist and pass, along with three supporting methods for the other realistically-reachable scenarios. This is the first task in the entire pipeline to run its own tests against a real Postgres Testcontainer **and** a real Kafka broker rather than mocks — directly proving R13/R14/O6/L5 rather than arguing them from unit-level argument matching.

**(2) Does it satisfy every acceptance criterion (frozen brief, Phase 4)?** All three (AC1–AC3) are satisfied: AC1 (R13 dedupe), AC2 (R14, all three realistically-reachable cross-event-type staleness scenarios), AC3 (O6 forward sequence, now also covering the invoice-state transition and the address-poisoning flag per Phase 8/11 findings).

**(3) Does it violate any LOCKED decision?** No. L1/L12/L14 all hold, unaffected by this test-only task. The externally-provisioned-Kafka-broker design (rather than a Testcontainers Kafka image) was itself a deliberate Phase 4 decision, re-affirmed at Phase 9 after Kimi's Phase 8 Finding 1 incorrectly claimed it contradicted that same decision — verified directly against `04-frozen-task-brief.md` and rejected with citations.

**(4) Remaining risks (carried forward, not blocking this task's own PASS):**
- **External Kafka broker dependency** (Phase 8 Finding 1 / Phase 11 Gap 5): this test requires `services/auth/compose.local.yaml`'s Kafka service running on `localhost:9094` before it can run at all. A `@BeforeAll` fail-fast check now gives a clear `IllegalStateException` naming the exact compose command if it's not up, rather than a confusing 40s `Awaitility` timeout. Any CI pipeline running this suite must start that compose stack first — a real, disclosed environmental requirement, not a code gap.
- **Same-event-type staleness is contractually unreachable in a real end-to-end test** (Phase 2 Decision 2, re-confirmed at Phase 3/8/11): every `chain.tx.*` schema's own idempotency key is fixed per `(chain, txHash, eventtype)`, so a second same-event-type message (e.g. a lower confirmation count) is dedupe-blocked by R13 before ever reaching R14's staleness-comparison logic. The three cross-event-type scenarios tested are the full realistically-reachable set; this is dispositioned, not a residual gap.
- **Pre-existing, found and fixed earlier this session, unrelated to T14's own scope but discovered while making this task's test runnable for the first time:** two production cron expressions (`themistra.payment.ledger.anchor.cron`, `themistra.payment.invoice.expiry-sweep.cron`) were in 5-field Unix cron format, which Spring's `CronExpression` parser rejects (6-field, seconds-first) — meaning the real application had apparently never been able to start as a live Spring Boot process anywhere in this pipeline until this fix. Already fixed and committed (`a88bc44a`), disclosed in `06-implementation-notes.md`; not a T14 regression, carried forward as context only.
- **Pre-existing, unrelated:** none remaining — `InvoiceRepositoryIntegrationTest` (T08's own defect) and `SchemaBaselineMigrationIntegrationTest` staleness were both fixed earlier this session (`277a31b6`), before T14 began.
