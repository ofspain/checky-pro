# auth · T20 · Phase 7 — Self Review

Findings only, ranked by severity. Fixes are Phase 9's job.

---

1. **Issue:** The mechanism R26/R27 depend on — `TokenClaimsCustomizer` reading `context.getPrincipal() instanceof TotpStepUpAuthenticationToken` at token-issuance time — is unverified against how `JdbcOAuth2AuthorizationService` actually persists the authorization's principal, and I have reason to believe it will silently fail.
   **Severity:** High.
   **Evidence:** `token/TokenClaimsCustomizer.java:54`. `token/AuthorizationServiceConfig.java` wires `JdbcOAuth2AuthorizationService` (unchanged, existing) as the `OAuth2AuthorizationService`. I decompiled the actual dependency jar (`spring-security-oauth2-authorization-server-1.5.1.jar`) rather than assuming: `JdbcOAuth2AuthorizationService$OAuth2AuthorizationRowMapper` holds a `com.fasterxml.jackson.databind.ObjectMapper` field and a `parseMap(String)` method — the authorization's principal is persisted as **Jackson-serialized JSON**, not Java serialization. Spring Security's own Jackson modules (`SecurityJackson2Modules`, `OAuth2AuthorizationServerJackson2Module`) ship mixins for its own standard types (`UsernamePasswordAuthenticationToken`, `User`, etc.) but have no knowledge of an application-defined `Authentication` subclass unless the app registers one. `authn/TotpStepUpAuthenticationToken.java` has a **private constructor and no public setters** — exactly the shape Jackson's default bean deserialization cannot reconstruct — and no Jackson module/mixin was registered anywhere in this diff or in `SecurityChainsConfig`/`AuthorizationServiceConfig`.
   **Recommendation:** Verify empirically before trusting this — it's exactly the category of risk `auth-decisions.md` (D-016, D-019) already flagged elsewhere in this codebase as "not part of a contract worth depending on blindly" without running it, and I couldn't run it here (no Docker in this environment). A Testcontainers-backed test exercising the full `/login` → `/oauth2/authorize` → `/oauth2/token` path with a confirmed-MFA account is the fastest way to find out whether this throws at persistence time, or — worse, silently — deserializes back to something that fails the `instanceof` check and always reports `amr: ["pwd"]` even after a successful MFA login (R26 quietly broken with no error anywhere). If it fails, the safer fix is likely to stop carrying the fact in a custom `Authentication` subclass at all, and instead add a synthetic `GrantedAuthority` (e.g. `SimpleGrantedAuthority("OTP_VERIFIED")`) to the existing `UsernamePasswordAuthenticationToken`-shaped result — `GrantedAuthority` collections are already covered by Spring Security's built-in Jackson support for standard token types.

2. **Issue:** `TotpAuthenticationProvider.verifyMfaCodeOrFail`'s broad `catch (RuntimeException e)` collapses genuine infrastructure failures into the same silent "bad credentials" path as ordinary wrong-code attempts, with no distinguishing log line.
   **Severity:** Medium.
   **Evidence:** `authn/TotpAuthenticationProvider.java:119-122`. If `MfaService.verifyTotpCodeForLogin`'s `mfaSeedEncryption.decrypt(...)` call throws `MfaEncryptionException` (a KMS outage, per D-025's accepted trade-off of a KMS round-trip on every verification), or any other unexpected `RuntimeException` surfaces from deeper in the call chain, it is caught here identically to `InvalidTotpCodeException`/`InvalidRecoveryCodeException` and rewrapped as `BadCredentialsException`, with no log statement anywhere in the catch block. `LoginFailureHandler` (unchanged, downstream) also never logs the exception by design. The net effect: a KMS outage would appear only as an `mfa.failed` audit-event spike, indistinguishable from a credential-stuffing attempt to whoever is watching the security metrics `agents.md`'s Observability section calls for.
   **Recommendation:** Add a WARN-level log inside the catch block for exception types other than the three expected MFA-verification exceptions (or log unconditionally, since the message never needs to carry code/secret material) — this doesn't have to touch the uniform client-facing response at all, only restore operator visibility.

3. **Issue:** Combining the password-lockout counter with MFA-code failures means an MFA-enrolled user now shares one 5-attempt/30-minute budget across two independently-fallible inputs (password and TOTP), where before T20 the budget only ever had to absorb password mistakes.
   **Severity:** Medium (product/security-tuning judgment call, not a spec violation).
   **Evidence:** `authn/LoginFailureHandler.java` (unchanged) increments the lockout counter for any `ACTIVE`-account authentication failure without branching on cause — this was already true before T20, but T20 is what makes "correct password, wrong TOTP" a newly-reachable failure mode that now also spends from that same budget. L4 doesn't distinguish failure cause, so this isn't a LOCKED-decision violation, and it does have a real security upside (it also rate-limits TOTP brute-forcing, which nothing else in this task does). But it's a genuine, non-obvious behavioral consequence nobody explicitly signed off on — a user who fat-fingers their TOTP code 3 times after already getting the password right is now measurably closer to a 15-minute lockout than before this task existed.
   **Recommendation:** Confirm this is the intended behavior (I believe it's defensible and said so when resolving Phase 4 #2/#6, but "defensible" isn't the same as "explicitly decided") rather than let it stand as an unexamined side effect.

4. **Issue:** Neither the submitted TOTP code nor the recovery code is trimmed before use, and this is the first task that makes `MfaService.verifyRecoveryCode`/the TOTP path reachable from raw, user-typed/pasted HTTP form input.
   **Severity:** Medium (usability/correctness, not security — failures still fail uniformly either way).
   **Evidence:** `authn/TotpAuthenticationDetailsSource.java:21` (`request.getParameter("mfaCode")`, no `.trim()`) flows straight into `authn/TotpAuthenticationProvider.java`'s `verifyMfaCodeOrFail` (only a blank check, no trim) and its shape-dispatch regex `TOTP_CODE_SHAPE = "\\d{6}"`. A recovery code with incidental trailing whitespace (common from copy-paste out of a saved list) fails the hash lookup in `MfaService.verifyRecoveryCode` even though the "real" code was correct. A TOTP code with leading/trailing whitespace fails the `\d{6}` shape match and gets silently mis-dispatched to the recovery-code path instead of the TOTP path — still ends in the same uniform failure, so no security hole, but the user has no way to know their code was rejected for a whitespace reason rather than being wrong.
   **Recommendation:** `.strip()` the raw `mfaCode` once, at the point it's read (`TotpAuthenticationDetailsSource.buildDetails` or the top of `verifyMfaCodeOrFail`), before the blank check and shape dispatch.

5. **Issue:** Holding a DB transaction open across a KMS network round-trip (`MfaSeedEncryption.decrypt`) is now on the interactive login hot path, not just the low-frequency enroll/confirm path it was previously confined to.
   **Severity:** Low (inherited pattern, traffic-profile change only).
   **Evidence:** `mfa/MfaService.java:224-241` (`verifyTotpCodeForLogin`, `@Transactional`, calls `mfaSeedEncryption.decrypt(...)` mid-transaction) — the same shape as the existing `confirm`/`disable` methods, not a new pattern I introduced. What's new is the call frequency: every MFA-required login now does this, versus the one-time enrollment/rare-disable frequency this pattern was originally accepted for.
   **Recommendation:** Not a correctness defect and not something to change unilaterally (the transactional-conditional-update pattern this method relies on for replay-safety genuinely needs the transaction). Worth a note for whoever owns capacity planning, not a code change.

6. **Non-issue, confirmed correct on review:** the literal role-name strings `"MERCHANT"`/`"ADMIN"` in `TotpAuthenticationProvider.MFA_MANDATORY_ROLES` (`authn/TotpAuthenticationProvider.java:36`) match the codebase's established convention exactly — verified against `RoleServiceTest`/`AdminAccountRoleControllerTest`'s existing fixtures, which use the same bare uppercase strings with no `ROLE_` prefix. Checked specifically because a casing/prefix mismatch here would have silently disabled R24 entirely with no test failure to catch it; ruled out.

7. **Non-issue, confirmed correct on review:** `AccountUserDetailsService`'s elapsed-lockout precedent (T13/R18 — a `LOCKED` account whose interval has passed must still be able to complete the very login that unlocks it) is preserved. `TotpAuthenticationProvider.verifyAccountUsableOrFail` (`authn/TotpAuthenticationProvider.java:85`) reads `userDetails.isAccountNonLocked()`, which `AccountUserDetailsService` already computes correctly via `LockoutService.isCurrentlyLocked` — this task's provider doesn't recompute or second-guess that value, so the precedent carries through unchanged.
