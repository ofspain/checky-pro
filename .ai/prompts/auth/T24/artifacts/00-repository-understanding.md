# auth · T24 · Phase 0 — Repository Understanding

## 1. Architecture summary

`services/auth` is a Spring Boot 3.5.4 / Java 21 module, package-by-feature under `com.themistra.auth`, acting as the platform's identity issuer (Spring Authorization Server). Persistence is PostgreSQL via JPA + Flyway. Every cross-service-relevant state change goes through an outbox table in the same transaction as the write; `AuditService.record(...)` is "the only sanctioned way any module writes to the audit trail" (its own Javadoc) — it both inserts an append-only `auth_audit` row and mirrors a reduced view to Kafka's `auth.security.audit` topic, in one call, `REQUIRES_NEW`-isolated from the caller's own transaction. Security is zero-trust JWT validation everywhere except a CI-enforced public-endpoint set; role-based authorization on HTTP endpoints is `@PreAuthorize`-driven (`ArchitectureTest.admin_controller_handlers_require_preauthorize` compiles this into a build-breaking rule for `Admin*` controllers specifically). Module boundaries (no feature module imports another's entity; repositories always package-private) are ArchUnit-enforced.

## 2. Existing code this task touches

- **`apikey.ApiKey` / `apikey.ApiKeyRepository`** (T23, complete) — the entity and repository this task's service layer will call. `ApiKeyRepository.findByPrefix(String)` returns `List<ApiKey>` (no DB-level uniqueness on `prefix`); `ApiKey.create(...)` requires `accountId`, `prefix`, `keyHash`, `name`, `scopes`, `createdAt`, and generates its own `keyUuid`. No mutators exist yet for `lastUsedAt`/`revokedAt`/`name` — T23's Javadoc explicitly left these for T24/T26 to add "following whatever concurrency shape that behavior actually needs."
- **The unresolved L7-vs-`VARCHAR(16)` conflict, explicitly deferred to this task.** T23's frozen brief (disposition #1) recorded two options without choosing: (a) amend L7 so the suffix is ≤8 characters, fitting the existing `prefix VARCHAR(16)` column, or (b) accept a new migration widening the column to `VARCHAR(32)`. This task cannot generate an L7-compliant key ("Generate `ck_live_<suffix>.<secret>`" is literally in T24's task statement) without resolving this first — it is a genuine Phase 1/2 blocker, not optional background.
- **`mfa.MfaService.hasConfirmedTotpEnrollment(UUID accountUuid)`** (T18/T20) — read-only, no side effects, exactly the check T24's task statement's "require... confirmed MFA" needs. Already public.
- **`authz.RoleService.resolveEffectiveRoles(UUID accountUuid)`** — returns `Set<String>` of the account's effective role names (direct + template-expanded). This is the established, already-public mechanism for a service to check "does this account hold role X" outside of `@PreAuthorize` — relevant because T24 has no controller of its own (T26 does) and the task statement's "require `MERCHANT`" phrasing is ambiguous about which layer enforces it (see Known Gaps).
- **`common.Hashing.sha256(String)`** — SHA-256 hex digest, used by `MfaService`/`RecoveryCode`/`VerificationToken` for hash-and-compare-by-repository-lookup patterns. It has **no constant-time comparison method** — T24's task statement explicitly calls for "constant-time hash compare," which does not exist anywhere in this codebase yet. `design.md`'s package map already anticipates a new `apikey/ApiKeyHasher.java` file for this.
- **`account.AccountService`** — `getByUuid(UUID)` returns `AccountResponse`; no method exposes the internal `Long` id (by design — internal PKs never leave the service). Whichever resolution pattern T24 needs (account UUID → internal `accountId` for `ApiKey.create`) will need either a repository-level native lookup (the `findAccountIdByUuid` pattern `MfaEnrollmentRepository`/other repositories already use) or an equivalent added to `ApiKeyRepository`.
- **`themistra.auth.api-key.prefix=ck_live_`, `themistra.auth.api-key.token-ttl-minutes=10`** (`application.properties`) — already configured; `token-ttl-minutes` is for T25's JWT issuance (out of this task's scope), `prefix` is directly relevant to key generation.

## 3. Established patterns to follow

- **Service class shape** (`MfaService`, `RoleService` are the closest analogs — both orchestrate a feature's business logic over its own module's repositories plus `AuditService` and a `Clock`, constructor-injected, no field injection):
  - `@Service`, all dependencies constructor-injected, `Clock clock` injected (never `Instant.now()` inline).
  - Public methods are `@Transactional` (mutating) or `@Transactional(readOnly = true)` (queries); private helpers do the repeated internal work (`resolveAccountId`, `requireActiveAccount`-style guards).
  - A dedicated `record...Audit`/`auditAssignment`-style private helper wraps every `auditService.record(new RecordAuditEventRequest(...))` call, keeping the six-argument constructor call in one place.
  - Domain-specific checked failures are distinct `RuntimeException` subclasses (`MfaAlreadyEnrolledException`, `InvalidTotpCodeException`, etc.), not generic exceptions with a message — each maps 1:1 to an `@ExceptionHandler` in a module-scoped `*ExceptionHandler` (`@RestControllerAdvice`) class producing an RFC 9457 `ProblemDetail` via `ProblemTypes`.
  - **Directly relevant precedent for R33's "uniform 401" requirement:** `AccountExceptionHandler.onVerificationTokenRejected` is this codebase's existing template for "IF [several different failure reasons] THEN [one uniform response]" — one exception class, one handler, fixed status/type/title, "never distinguishes [reason A] from [reason B] from [reason C]" (its own Javadoc). R33 (revoked/expired/malformed/hash-mismatch → uniform 401) is the same shape and should very likely follow the same one-exception-one-handler pattern rather than four distinct exceptions.
- **Hashing/lookup-then-verify pattern**: `MfaService.verifyRecoveryCode` and `RecoveryCodeRepository.findByAccountIdAndCodeHash`/`markUsed` show the established shape for "hash the presented secret, look up by hash, atomically consume" — though recovery codes hash the *entire* presented value and look up by that hash directly (no separate prefix step), whereas API keys per L7's design need a two-part lookup (prefix for the DB query, then a **constant-time** comparison of the secret component) — a genuinely different shape this task introduces, not a copy of the recovery-code pattern.
- **Role checking, service layer**: no existing service method currently gates its own logic on `RoleService.resolveEffectiveRoles(...).contains(roleName)` — every role check in the current codebase happens via `@PreAuthorize` on a controller method. T24 has no controller. Whether T24's `create(...)` method should independently re-verify the `MERCHANT` role and confirmed-MFA precondition itself (defense-in-depth, matching `MfaService.requireActiveAccount`'s pattern of re-checking preconditions a caller "should" have already established) is a real design decision for Phase 1/2, not a settled convention to just follow.
- **Persistence/Flyway**: unchanged conventions from T23 — `api_keys` table already exists (V1); if the L7-width conflict resolves toward widening the column, that would be a new `V7` migration, additive only.

## 4. Testing conventions

- Unit tests: plain JUnit, no Spring context, fixed `Clock`. `MfaService` has no direct unit-test precedent shown in this exploration (its tests are integration-level), but pure-logic pieces like a future `ApiKeyHasher` (constant-time compare has no DB dependency) are exactly the kind of thing this codebase unit-tests in isolation (c.f. `LockoutStateMachine`, `TotpVerifier`).
- Persistence/service integration tests: Testcontainers (Postgres + Kafka), `*PersistenceIntegrationTest`/`*IntegrationTest` naming, `@SpringBootTest` + `@Import(TestcontainersConfiguration.class)`.
- `package.md` §8 named tests scoped to this task: `shouldCreateApiKeyAndShowPlaintextExactlyOnce`, `shouldRejectRevokedOrUnknownApiKeyWithUniform401` — both service-level behaviors (creation, exchange rejection), consistent with T24 being the service-layer task.
- ArchUnit (`ArchitectureTest`) will apply to any new `ApiKeyService` the same way it applies to every other service: no `Account` entity import (L12), any repository stays package-private.

## 5. Known gaps / unknowns

- **The L7-vs-`prefix VARCHAR(16)` conflict must actually be resolved by this task**, not just acknowledged — T24 cannot "Generate `ck_live_<suffix>.<secret>`" per L7's literal 24-character-suffix definition without either L7 being amended or the column being widened. This is the single largest open item carried into Phase 1.
- **Which layer enforces "require `MERCHANT` + confirmed MFA"** is genuinely unclear from the task statement and this codebase's own precedent split (role checks are currently `@PreAuthorize`-only; MFA-confirmation checks like `hasConfirmedTotpEnrollment` are already service-layer). T24 has no controller (T26 does), so if the intent is "T24's `create()` method itself must enforce this," the service needs to accept and check the caller's identity/roles directly; if the intent is "T26's controller enforces `@PreAuthorize`, T24 only implements the create logic assuming the precondition already holds," that's a materially smaller task. I do not know which the spec intends — this is a Phase 1/2 question, not resolved here.
- **Whether T24 needs to touch `EventTopics.java`.** `design.md`'s config snippet shows an aspirational `"api-key" → "auth.email.requested"` aggregate-type mapping that was never actually added to the current `EventTopics.java` (only `"account"`, `"audit"`, `"verification-token"` exist today). R30's audit requirement is already fully satisfiable via `AuditService.record(...)` alone (which publishes to the fixed `"audit"` aggregate type internally, independent of `EventTopics`). I do not know whether a *separate* lifecycle/notification event (distinct from the audit mirror) is actually required for API key creation, or whether that stale design.md snippet is leftover from an earlier, since-abandoned design — this needs Phase 1 clarification, not an assumption.
- **`package.md` §11 Q3** ("max active API keys per merchant? scopes beyond `merchant.api`?") remains unresolved in the spec itself. Directly relevant to `create(...)`'s scope this time (unlike T23) — if a cap exists, `create` needs to enforce it; if not, that's itself a decision to record. Not resolved here.
- **Exact `accountId` resolution mechanism** for `ApiKeyService` — `ApiKeyRepository` currently has no UUID→id lookup method (T23 deliberately left it out as speculative/YAGNI). T24 is the first real caller, so this is exactly the point where such a method (mirroring `MfaEnrollmentRepository.findAccountIdByUuid`) should likely be added — a Phase 2 design decision, not assumed here.
